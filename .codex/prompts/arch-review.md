# 任务模板：架构评审 / 自查

> 用法：
> ```bash
> codex "按 .codex/prompts/arch-review.md 评审 apps/gateway/src/modules/system/user"
> ```

## 角色

你是本仓库的高级系统架构师。任务是**找违反架构规则的地方**，按严重度排序输出，**不修改代码**（除非我明确要求修）。

## 第一步：读规则

```
docs/企业级架构规范与扩展指南.md
  ├─ 1.4  架构不变式（7 条）        ← 最高优先级
  ├─ 2.   四层模型                  ← 代码属于哪一层
  ├─ 3.2  库间依赖矩阵              ← 允许/禁止的依赖
  ├─ 3.4  业务模块之间的依赖
  ├─ 3.5  全局模块白名单
  ├─ 4.   横切关注点落位            ← 有没有重复造轮子
  ├─ 5.2-5.4  响应信封与业务码
  ├─ 6.   业务模块设计规范
  ├─ 14.  分层反模式清单（18 条）   ← 逐条对照
  └─ 17.4 代码评审清单
```

## 第二步：逐条对照

### A. 架构不变式（违反 = P0）

| # | 检查项 | 判定 |
| --- | --- | --- |
| I1 | 有没有 `libs` import `apps`？有没有反向依赖？ | 有 → P0 |
| I2 | 出参是否都过了 Response DTO？敏感字段是否 `@Exclude()`？ | 否 → P0（泄露） |
| I3 | 响应是否符合统一信封？有没有手拼 `{code,data,message}`？ | 否 → P0 |
| I4 | 有没有运行期读配置 / 读 `process.env`？ | 有 → P0 |
| I5 | 业务失败是否用 `BusinessException`？有没有 `throw new Error()` 表示业务失败？ | 否 → P1 |
| I6 | 日志是否含凭据？是否有请求 ID 关联？ | 否 → P0 |
| I7 | 有没有字符串拼接 SQL？ | 有 → P0 |

### B. 分层与依赖（第 2、3 章）

- [ ] 代码是否放在了正确的层？（L3 业务逻辑是否漏到了 L4 或 L2）
- [ ] 模块间依赖是否单向？有没有 `forwardRef`？
- [ ] 有没有跨模块直接查别人的表？
- [ ] 新增的 `@Global()` 是否在白名单内？
- [ ] 库间引用是否用了深路径（而不是 barrel）？

### C. 反模式（第 14 章，逐条过 A1-A18）

重点看这几条，出现频率最高：

| # | 反模式 |
| --- | --- |
| A2 | Service 注入 `@Req()` / `ExecutionContext` |
| A3 | Controller 里直接 `prisma.xxx` |
| A4 | Service 返回 Prisma 模型给 Controller |
| A6 | `throw new Error()` 表示业务失败 |
| A8 | 跨模块直接查别人的表 |
| A10 | 把会话/限流塞进 `CacheService` |
| A11 | 事务里删缓存/发消息 |
| A13 | 往 `BUSINESS_CODE` 加业务错误码 |
| A15 | Response DTO 字段漏 `@Expose()` |
| A16 | 列表接口不分页 |

### D. 契约（第 5 章）

- [ ] 错误码是否在模块分配的段位内？是否复用了已占用的码？
- [ ] 契约变更是否向后兼容？（5.5 的表格）
- [ ] `errors` 字段是否只在字段校验失败时出现？
- [ ] 5xx 是否透传了内部异常消息？

### E. 数据层（第 8 章）

- [ ] 列表查询是否走 `paginate()`？`pageSize` 是否封顶？
- [ ] 软删除条件是否显式写了 `delFlag`？
- [ ] 事务回调内是否只用了 `tx`？副作用是否在提交后？
- [ ] 有没有 N+1（循环里 `await` 查询）？
- [ ] `select` 和 `omit` 有没有同时用？

### F. 工程（第 13 章）

- [ ] 相对导入是否带 `.js`？
- [ ] 纯类型导出是否用了 `export type`？
- [ ] 有没有 `any` / `console.log`？
- [ ] DTO 文件名是否以 `.dto.ts` 结尾？
- [ ] 有没有手写 `@ApiProperty()`？
- [ ] 注释是否在写「为什么」而不是「是什么」？

## 第三步：输出

按严重度分组，**每条都要给出文件:行号和具体改法**：

```markdown
## P0 —— 必须修（违反架构不变式 / 安全漏洞）
1. `<文件>:<行号>` —— <问题>。违反 <不变式编号/章节>。
   改法：<具体怎么改>

## P1 —— 应该修（违反设计规范，但不会立即出事）
...

## P2 —— 建议（风格/可读性）
...

## 架构债
- <与 17.2 的 D1-D8 对得上的，标注编号>

## 做得对的地方
- <列出 2-3 条，避免只输出负面信息>

## 结论
<一句话：这个模块的架构健康度，能不能合并>
```

## 评判标准

| 严重度 | 判据 |
| --- | --- |
| **P0** | 会导致数据泄露、安全漏洞、契约崩坏，或违反 1.4 的 7 条不变式 |
| **P1** | 违反分层/依赖/设计规范，当前不出事但会阻碍演进 |
| **P2** | 风格、可读性、命名 |

**不要把所有问题都标 P0。** 严重度失真等于没有严重度。

## 禁止

- ❌ 只输出"建议优化"这种没有具体改法的意见
- ❌ 把"我不喜欢的写法"标成 P0
- ❌ 评审时顺手改代码（除非明确要求）
- ❌ 忽略 17.2 已记录的架构债，重复报告同一件事而不标注编号
