# 任务模板：修 bug

> 用法：
> ```bash
> codex "按 .codex/prompts/fix-bug.md 修这个问题：<现象/报错/复现步骤>"
> ```

## 角色

你是本仓库的高级后端工程师。任务是**定位根因并最小化修复**，不是重构。

## 第一步：先别改代码

按这个顺序排查，**每一步都要有证据**：

```
1. docs/项目文件地图与架构说明.md 第 14 章（已知问题 11 条）
   → 是不是已知缺口？例如「没有 ValidationPipe」「migrations 未入库」
2. docs/企业级架构规范与扩展指南.md 第 16 章（ADR 9 条）
   → 这个"奇怪"的实现是不是有意的？改之前必须确认
3. logs/gateway/error.log 或 gateway.log
   → 用 req.id 串起整个请求
4. 相关源码
```

**第 1、2 步不能跳过。** 很多"bug"是有意的设计（`toOptionalNumber` 返回 `NaN`、`CacheService.clear` 抛错、`LoggerTransport` 关闭时先 `ref()`），改掉就是引入新 bug。

## 第二步：写复现测试

**在改任何实现代码之前**，先写一个失败的测试。

| bug 类型 | 测试放哪 | 怎么写 |
| --- | --- | --- |
| 纯函数 / 单类 | 与被测文件同目录 `<name>.spec.ts` | 直接调用，断言输入输出 |
| Service / 模块 | 同目录 `<name>.spec.ts` | `Test.createTestingModule` + mock 外部依赖 |
| 接口行为 | `test/<name>.e2e-spec.ts` | 真实 `AppModule` + `app.inject()` |
| 配置解析 | `libs/config/src/domains/*.spec.ts` | `xxxDomain.parse({...}, { environment: 'test' })` |

跑一遍确认它**确实失败**，并把失败输出贴出来。没复现就不要修。

## 第三步：定位根因

输出一句话根因，格式：

```
根因是 <具体机制>，不是 <表面现象>。
证据：<文件:行号> / <日志片段> / <测试输出>
```

**禁止**用"可能是""应该是"来掩盖不确定。不确定就继续查，或者明说"未确定，需要 <什么信息>"。

## 第四步：最小化修复

规则：

| 规则 | 说明 |
| --- | --- |
| 只改必要的行 | 不重构、不重命名、不调格式 |
| 不扩大范围 | 发现别的问题只**报告**，不顺手改 |
| 保持现有风格 | 照抄同文件的写法 |
| 不引入新依赖 | 除非明确说明理由并等我确认 |
| 改公共契约要谨慎 | 改 Response DTO / 错误码 / 响应信封 = 破坏性变更，先停下来说 |

## 第五步：验证

```bash
pnpm test                    # 新写的复现测试必须通过
pnpm lint && pnpm build      # 不能引入新问题
pnpm test:e2e                # 涉及接口/数据层时必跑
```

同时确认：**改动前就存在的其他失败测试，改动后依然失败**（不要"顺手修好"或"顺手弄坏"）。

## 汇报格式

```markdown
## 根因
<一句话>。证据：<文件:行号 / 日志片段>

## 复现测试
- 文件：<路径>
- 修复前输出：（贴失败输出）
- 修复后输出：（贴通过输出）

## 改动
- <路径:行号>：<改了什么，为什么这样改>

## 影响面
- 受影响的接口/模块：<列出>
- 是否改动公共契约：<否 / 是，说明>

## 验证结果
（贴 pnpm test / lint / build 的实际输出）

## 范围外发现（仅报告，未修改）
- <问题描述>：建议 <怎么处理>
```

## 禁止

- ❌ 没复现就"看起来是这里"直接改
- ❌ 顺手重构、顺手优化、顺手改名
- ❌ 用 `try/catch` 吞掉异常来"修复"报错
- ❌ 为了让测试通过而改测试的断言（除非断言本身写错了，且要说明理由）
- ❌ 隐瞒未解决的问题
