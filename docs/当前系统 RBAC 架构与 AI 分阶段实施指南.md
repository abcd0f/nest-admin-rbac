# 当前系统 RBAC 架构与 AI 分阶段实施指南

> 本文定义如何在当前仓库中实现企业级 RBAC。目标是让 AI 按阶段、小步、可验收地交付。
> **数据模型冻结：实施过程不得修改现有表结构、Prisma model、迁移或数据库约束。** 如果某项目标确实无法由现有结构表达，必须先报告具体缺口和影响，停止该项，不得自行扩表或改字段。

## 1. 文档边界与实施原则

本文件是 RBAC 的实施路线，不取代仓库架构规范。发生冲突时依次遵循：

1. `docs/企业级架构规范与扩展指南.md`：分层、依赖、请求响应契约和代码规范的最高约束。
2. `docs/项目文件地图与架构说明.md`：当前代码实际状态的事实来源。
3. 本文：在以上约束下规划 RBAC 的目标行为和阶段。

每个阶段由 AI 单独执行。开始前先检查代码和相关文档，结束时汇报文件、行为、测试实际输出、遗留问题；不得把未运行的检查写成通过。每阶段只做本阶段及其必要依赖，不顺手重构无关代码。

## 2. 当前基线

### 2.1 已有能力

| 能力 | 当前状态 | 对 RBAC 的用途 |
| --- | --- | --- |
| 模块化单体与 NestJS/Fastify 入口 | 已有 | 业务模块位于 `apps/gateway/src/modules/` |
| Prisma 7 与 PostgreSQL | 已有 | 领域服务通过 `PrismaService` 访问数据 |
| 用户、角色、菜单、部门、职位及关联模型 | 已有 | 作为 RBAC 数据基础，字段和关系保持不变 |
| 密码哈希 | `libs/crypto` 有 Argon2id `PasswordHashService` | 登录密码校验和创建/重置密码时哈希 |
| Redis 连接 | `RedisConnection` 由 `RedisModule` 单例管理 | 会话/权限状态使用共享 Redis 客户端 |
| 通用 `CacheService` | 已有，读失败会降级为未命中 | **不得**用于会话或权限快照，避免故障时绕过认证 |
| 统一响应与异常过滤 | 已有 | Controller 直接返回数据；业务错误走 `BusinessException` |
| DTO 白名单转换、分页 helper | 已有 | 出参 DTO 必须 `@Expose()`；列表走 `paginate()` |

### 2.2 尚未实现及需要特别处理的缺口

- `user` 模块目前主要是占位实现，没有真实用户管理闭环。
- 登录、认证凭证签发/验证、认证 Guard、权限 Guard、权限快照、菜单树和数据范围都尚未实现。
- 当前没有全局 `ValidationPipe`。DTO 装饰器不会自动校验、转换或应用默认值；认证和管理接口上线前必须先按架构规范 ADR-009 完成校验管线，或在明确的边界显式转换与校验。
- `SystemModule` 当前标记了 `@Global()`，是已知架构债。新增依赖应显式装配，不要扩大隐式依赖。
- Redis 可能通过配置关闭。会话认证不能在 Redis 不可用时降级成匿名或允许访问；启动配置和运行时故障均应失败关闭。

### 2.3 冻结的数据模型

实现前核对 `prisma/models/`。当前相关模型是：

- `User` / `UserRole`：用户身份及用户-角色多对多；用户包含 `password`、`status`、`delFlag`、`deptId`。
- `Role` / `RoleMenu`：角色及角色-菜单多对多；角色包含 `roleKey`、`dataScope`、`status`、`delFlag`。
- `Menu`：目录、菜单、按钮共用，`menuType` 区分类型，`perms` 是操作权限标识。
- `Dept` / `RoleDept`：组织层级及自定义角色部门范围；`ancestors` 保存含自身的物化路径。
- `Post` / `UserPost`：职位关系，不是授权角色，不得混作权限来源。

字段语义以 schema 和已有数据为准。尤其 `status`、`delFlag` 的具体取值要核对现有约定和种子数据，不能凭空定义。当前模型没有独立的用户会话/刷新令牌表、账户锁定字段、登录失败计数、权限版本字段或租户字段；本次架构不得通过新增字段模拟这些能力。若安全需求要求持久化刷新令牌、精确账户锁定或租户隔离，列为后续数据模型决策，不纳入无 schema 变更的实现。

## 3. 目标架构与边界

```text
HTTP 请求
  -> DTO 校验与转换
  -> AuthenticationGuard：解析凭证、加载有效身份
  -> PermissionGuard：按路由元数据检查操作权限（默认拒绝）
  -> Controller：只做传输层编排
  -> Domain Service：用例、授权边界、事务
  -> PrismaService / RedisConnection
```

### 3.1 代码归属

```text
apps/gateway/src/modules/
├── auth/                         # 登录、登出、当前用户/权限查询、认证策略
└── system/
    ├── user/                     # 用户业务与用户-角色/部门关联管理
    ├── role/                     # 角色业务与角色-菜单/部门授权管理
    ├── menu/                     # 菜单树与权限标识管理
    └── dept/                     # 部门树与数据范围支持

libs/core/src/guards/             # 通用 HTTP Guard 若符合平台层职责
libs/core/src/decorators/         # 通用授权元数据装饰器（不得依赖业务模块）
```

可复用且与 Nest/数据库无关的权限标识匹配逻辑，只有在确有跨模块复用时才考虑独立纯函数库；不要让 `libs/*` 导入 `apps/*`。数据库查询和 RBAC 领域策略归业务模块，不塞入 `DatabaseService` 或通用平台库。跨模块协作使用导出的窄服务接口，避免直接查别的模块表和双向依赖。

### 3.2 身份认证与授权职责

- **认证回答“是谁”**：验证凭证、确认用户仍有效、生成可信的当前请求身份上下文。客户端传来的 userId、roleKey、权限列表一律不可信。
- **功能授权回答“能做什么”**：从数据库权限事实构造当前权限快照；Guard 对路由声明的 `perms` 执行匹配，默认拒绝。
- **数据授权回答“能操作哪些记录”**：Service 根据用户的有效角色 `dataScope` 与 `RoleDept`，构造数据库 where 条件。Guard 的功能权限通过不等于数据范围通过。
- **菜单仅用于 UI 呈现**：菜单树和按钮权限可以由同一授权事实计算，但隐藏菜单/前端不显示不是 API 安全边界。

### 3.3 权限规则

1. 用户必须存在、未软删除且状态有效；分配给用户的角色也必须未软删除且有效。任何相关状态无效时拒绝认证/授权或从有效集合剔除，按操作场景测试。
2. 有效角色的 `RoleMenu` 汇总得到 `Menu.perms`；忽略无效菜单及空权限标识。用户多个角色的功能权限取并集。
3. 权限标识建议采用 `system:user:list` 形式，并与 `Menu.perms` 精确对应；通配符若启用，必须只实现受控的段级通配（如 `system:user:*`），严禁用不受约束的子串匹配。超级管理员绕过规则只有在现有表数据能稳定识别且有审计测试时才可启用，不得硬编码未经确认的用户名或 ID。
4. 菜单树只返回用户有权访问的目录/菜单，并保留父级路径所需节点；按钮权限不应伪装成导航节点。
5. 登录成功后的权限快照应由服务端构造，快照内容至少包括 userId、roleKeys、权限标识集合和所需数据范围元信息；不得缓存密码、令牌明文或不必要个人信息。
6. 任何缓存只用于性能，数据库/身份校验规则仍是权威。失效策略不完整时宁可缩短 TTL 或回源，不可依赖长时间陈旧快照实现安全授权。

### 3.4 凭证与 Redis 约束

开始认证实现前，先核对现有依赖、配置和 `libs/crypto/README.md`，并明确签名算法、密钥来源、过期时间、刷新/撤销策略。不得自行发明不安全 token 格式，不得把密钥写入代码或提交到 YAML。没有已批准的 JWT 库/策略时，先提交依赖与算法决策供项目配置，不要手写 JWT 密码学。

会话或撤销状态若存 Redis，必须直接复用 `RedisConnection.client`，使用专属、可辨识的 key 前缀及 TTL，并明确 Redis 断连的失败关闭行为；不得通过会降级为 cache miss 的 `CacheService`。单纯无状态短期访问令牌不能即时撤销；应在文档和验收中说明其撤销窗口，或采用服务端会话标识检查。登出和管理员禁用/改权后的失效应有明确可测试语义。

## 4. 实施顺序与阶段验收

各阶段依次执行；下游阶段不能假定前一阶段已通过。涉及 HTTP 或数据访问的阶段运行相关 e2e。每阶段验收命令至少包括：

```bash
pnpm lint
pnpm build
pnpm test
```

需要数据库的 e2e 还需运行 `pnpm test:e2e`。仓库基线要求的命令均需实际执行并报告退出结果；发现无关既有失败应注明，不得掩盖或修复范围外内容。

### 阶段 0：基线盘点与约束确认

**目标**：为后续实施建立可复核基线，不写业务代码。

**任务**：检查架构规范第 2-4 章、6、8-10、12-17 章相关部分；检查文件地图、用户模块、schema、配置、Redis、密码哈希、响应异常实现。确认工作树已有变更并避让。列出冻结表模型和认证所需但当前缺失的决策。

**验收**：提交阶段报告，含当前代码位置、已有能力、缺口、认证 token 策略待决项；明确本阶段未修改 schema、迁移和生成物。

### 阶段 1：请求 DTO 校验与业务错误基础

**目标**：确保认证与管理端点收到可信、规范的输入。

**任务**：按 ADR-009 实现全局 ValidationPipe（`transform`、`whitelist`、`forbidNonWhitelisted` 和统一 `BusinessException` 校验错误），补齐扁平字段错误映射。确认 Fastify/Nest 的全局注册位置、统一响应信封和错误码段位；认证错误使用稳定的认证错误码，不泄露账户是否存在、密码是否正确等敏感细节。

**验收**：校验错误契约测试；非法、未知字段和类型转换测试；回归现有 user 与 app e2e。若不能先全局启用，任何认证 DTO 必须显式转换校验并证明装饰器实际执行。

### 阶段 2：认证策略决策与 Auth 骨架

**目标**：搭建认证模块和凭证生命周期边界。

**任务**：落位 `auth` 模块、认证 DTO、错误码、认证策略接口和配置；按 3.4 决定并实现凭证验证/签发、到期、刷新或会话、登出撤销和 Redis 故障语义。密码核验复用 `PasswordHashService`。登录查询显式过滤软删除和停用用户；身份查询使用 BigInt 安全解析，避免精度丢失。

**验收**：登录成功/失败、未知用户与错误密码外部错误一致、禁用/删除用户、过期凭证、篡改凭证、登出和 Redis 不可用的测试；凭证及密码不得进入日志。没有完成的策略决策不能用临时弱实现跳过。

### 阶段 3：认证上下文与路由保护

**目标**：让受保护请求只能由服务端验证的身份进入。

**任务**：实现认证 Guard 和当前用户请求上下文；明确公共路由元数据，避免默认全局保护导致登录不可达或遗漏路由。认证失败走统一异常信封。认证与权限职责分开；不在 Controller 中校验 token，也不在 Service 注入 `@Req()` 或 `ExecutionContext`。

**验收**：匿名请求、无效/过期凭证、有效凭证、公共路由及路径覆盖测试；受保护路由默认拒绝；请求上下文 userId 不可由 body/query 覆盖。

### 阶段 4：权限查询、快照与权限 Guard

**目标**：把 `UserRole -> RoleMenu -> Menu.perms` 落成稳定的服务端授权判断。

**任务**：实现权限快照计算服务、权限装饰器/元数据、权限 Guard。显式过滤用户、角色、菜单状态及 `delFlag`；权限匹配用独立纯函数并覆盖精确匹配、通配边界、空权限、多个角色并集、无角色、停用角色/菜单。设计 Redis key、TTL、版本/失效或回源策略；角色菜单、用户角色、角色状态变更后清理相关快照。不得把仅失效某个用户却无法追踪关联人的问题藏起来：可采用短 TTL + 安全回源，或验证可行的全局授权版本策略，不扩表。

**验收**：权限匹配单测完整覆盖边界；Guard e2e 验证无权限拒绝、有权限通过、权限变更后按约定时间生效；Redis 断连不允许缓存 miss 被解释为授权通过。

### 阶段 5：角色与菜单管理闭环

**目标**：管理员能够通过现有表维护权限事实。

**任务**：新增 `role`、`menu` 业务模块及 DTO/Service/Controller；实现角色分页、详情、新增、修改、软删除/状态、角色菜单授权、菜单树和菜单权限标识管理。写操作在事务中同步关联表；校验引用对象存在、状态有效、树结构无环、菜单类型与字段规则一致、关键角色保护策略明确。所有列表用 `paginate()`，每个查询显式写 `delFlag: '0'`。响应仅通过白名单 Response DTO。

**验收**：角色 CRUD 与菜单授权 e2e；关联替换原子性；非法菜单树/越权管理测试；删除有用户关联角色时遵循明确规则且不破坏外键；OpenAPI DTO 展示正确。

### 阶段 6：用户角色分配与个人权限接口

**目标**：打通管理员分配与用户自助读取。

**任务**：实现用户角色分配、用户当前资料、当前角色/权限标识、可访问菜单树接口。所有管理接口要求相应权限；分配时防止越权指派高权限角色，且在事务中替换 `UserRole`。禁止用户通过提交 userId 读取或修改他人数据，除非通过显式权限规则允许。

**验收**：角色分配和快照更新 e2e；用户 A 不能读写用户 B；缺失功能权限拒绝；菜单输出不能作为 API 授权的替代。

### 阶段 7：部门数据范围

**目标**：实现 `Role.dataScope` 和 `RoleDept` 对业务查询的行级限制。

**任务**：按现有 `Role.dataScope` schema 注释解释代码值：`1` 全部、`2` 自定义、`3` 本部门、`4` 本部门及以下、`5` 本人、`6` 部门及以下或本人；先核对种子/业务数据后实现。自定义范围通过 `RoleDept` 表达；部门及下级利用 `Dept.ancestors` 的含自身路径。处理根部门、无部门用户、软删除部门和坏路径。多个角色的范围合并规则必须明确；通常范围取并集，不能简单取数值最小值。业务 Service 在原查询 where 条件中合并数据范围，禁止先查全量再内存过滤。

**验收**：每种范围及多角色组合的单测/e2e；验证查询 where 约束、无部门和异常层级默认拒绝/安全降级；任何跨部门访问均有可解释的权限依据。

### 阶段 8：安全收口、审计与运营验收

**目标**：确认 RBAC 具备上线可操作性。

**任务**：复核凭据密钥外置、TLS/代理信任、敏感日志、错误信息、暴力尝试限流、Redis故障行为、权限缓存失效、关键授权变更审计、OpenAPI 暴露面和安全默认值。当前限流是进程内计数，不可视为多实例安全防护；按上线要求确定共享限流实现或部署边界。禁止在日志记录密码、token、密钥或完整权限凭证。

**验收**：执行全量单测、构建、lint 和数据库 e2e；逐项完成架构规范 17.4 评审清单；手工验证典型越权场景；列出尚未解决的限制。发布前由系统负责人确认安全策略与撤销窗口。

## 5. 接口边界建议

以下是职责建议，不代表现有接口已实现；实际路径遵循项目 API prefix 与路由命名约定：

| 域 | 用例 |
| --- | --- |
| Auth | 登录、登出、刷新/续期（取决于认证策略）、当前用户、当前权限、当前菜单 |
| User | 用户分页/详情/创建/更新/软删除/状态、角色分配、部门关联 |
| Role | 角色分页/详情/创建/更新/状态/删除、角色菜单与自定义数据部门授权 |
| Menu | 菜单树/详情/创建/更新/状态/删除、权限标识维护 |
| Dept | 部门树与部门管理（按后续范围实现），供数据范围策略使用 |

每个接口先定义 Request DTO、Response DTO、权限标识和数据范围，再写 Service 用例。出参 DTO 每个公开字段必须 `@Expose()`；BigInt 输出字符串化，日期使用仓库规定的格式转换。Controller 不手拼 `{ code, data, message }`。

## 6. 测试设计

- **纯函数单测**：权限标识匹配、角色权限并集、菜单树裁剪、dataScope 合并与部门路径判断。
- **Service 单测**：有效用户/角色查询、软删除过滤、事务原子性、关联变更与快照失效。
- **Guard 测试**：匿名、无效凭证、缺失权限、通配符边界、公共路由和默认拒绝。
- **e2e**：登录及会话生命周期、完整请求保护链、管理权限、跨用户越权、部门数据范围、统一错误信封。
- **故障测试**：Redis 未配置/断连不能绕过认证授权；数据库或权限源不可用时采用失败关闭语义。
- 不用 mock 断言实现细节代替业务行为测试；测试应检查响应、数据库关联事实和拒绝边界。

## 7. AI 分阶段执行模板

将下面提示与本文件的指定阶段一起发给 AI：

