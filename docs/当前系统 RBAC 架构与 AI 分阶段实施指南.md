# 当前系统 RBAC 架构与 AI 分阶段实施指南（优化版）

> 本文定义如何在当前仓库中实现企业级 RBAC，目标是让 AI **按阶段、小步、可验收**地交付。
> **数据模型冻结**：实施过程不得修改现有表结构、Prisma model、迁移或数据库约束（含索引）。
> 若某项目标无法由现有结构表达，必须先报告「具体缺口 + 影响 + 可选方案」，**停止该项**，不得自行扩表或改字段。

## 0. 速览（TL;DR）

| 主题     | 决策                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 认证     | Redis 存储的**不透明会话令牌**（服务端可吊销），不使用无状态 JWT 作为唯一凭证                                |
| 功能授权 | `AuthenticationGuard → PermissionGuard`，**默认拒绝**，路由须显式声明 `@Public()` 或 `@RequirePermissions()` |
| 数据授权 | Service 层根据 `dataScope` 生成 Prisma `where`，**读、改、删一律施加**，不止列表                             |
| 权限快照 | Redis 存储，携带全局授权纪元（epoch），每次请求校验；Redis 异常**失败关闭**                                  |
| 越权防护 | 授权类写操作必须满足「只能授予自己已拥有的权限/角色」                                                        |
| 前端契约 | 菜单/按钮权限仅用于 UI 呈现；401/403 语义固定；权限变更后可感知并刷新                                        |
| 测试     | 纯函数先行（TDD），Guard/Service 集成测试，权限矩阵 + 负向用例为必选项                                       |

## 1. 文档边界与实施原则

1. `docs/企业级架构规范与扩展指南.md`：分层、依赖、请求响应契约、代码规范的最高约束。
2. `docs/项目文件地图与架构说明.md`：当前代码实际状态的事实来源。
3. 本文：在以上约束下规划 RBAC 的目标行为与阶段。

**通用执行规则**

- 每个阶段由 AI 单独执行。开始前先阅读相关代码与文档，**先确认事实再动手**（尤其是 `status`/`delFlag` 取值、`dataScope` 取值、种子数据）。
- 每阶段只做本阶段及其必要依赖，不顺手重构无关代码。
- 结束时必须汇报：改动文件、行为变化、**测试命令及实际输出**、遗留问题。**未运行的检查不得写成通过。**

## 2. 当前基线

### 2.1 已有能力

### 2.2 缺口与风险（实施前必读）

| 缺口 / 风险                                          | 影响                                                         | 处理方式                                                   |
| ---------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| `user` 模块基本是占位                                | 无用户管理闭环                                               | 阶段 5 补齐                                                |
| 无登录、凭证、Guard、权限快照、菜单树、数据范围      | RBAC 核心缺失                                                | 阶段 1–4                                                   |
| **无全局 `ValidationPipe`**                          | DTO 装饰器不会校验/转换/默认值，认证与管理接口存在输入面风险 | **阶段 0 前置**：按 ADR-009 完成校验管线，或在边界显式校验 |
| `SystemModule` 为 `@Global()`                        | 隐式依赖扩散，已知架构债                                     | 新增依赖显式装配，不扩大 Global                            |
| Redis 可被配置关闭                                   | 会话认证无法工作                                             | 启动与运行时均**失败关闭**（见 §3.4）                      |
| 无会话表、锁定字段、登录失败计数、权限版本、租户字段 | 部分安全能力无法持久化                                       | 用 Redis 实现易失态；持久化需求列为后续数据模型决策        |

### 2.3 冻结的数据模型

实施前核对 `prisma/models/`。相关模型：

- `User` / `UserRole`：用户及用户-角色多对多；用户含 `password`、`status`、`delFlag`、`deptId`。
- `Role` / `RoleMenu`：角色及角色-菜单多对多；角色含 `roleKey`、`dataScope`、`status`、`delFlag`。
- `Menu`：目录/菜单/按钮共用，`menuType` 区分类型，`perms` 为操作权限标识。
- `Dept` / `RoleDept`：组织层级及自定义数据范围；`ancestors` 保存**含自身**的物化路径。
- `Post` / `UserPost`：职位关系，**不是授权来源**，不得混入权限计算。

**事实核对清单（阶段 0 产出，写入阶段汇报）**

- [ ] `status` 的「有效」取值；`delFlag` 的「未删除」取值（以 schema 与种子数据为准）。
- [ ] `dataScope` 各取值的含义与对应枚举（全部 / 自定义 / 本部门 / 本部门及以下 / 仅本人，是否一致）。
- [ ] `Dept.ancestors` 的分隔符与首尾格式（直接决定「本部门及以下」的匹配写法）。
- [ ] `Menu.perms` 是否存在重复、空串、大小写不一致的历史数据。
- [ ] 现有索引是否覆盖权限聚合与部门路径查询；**若缺失只报告，不新增**。
- [ ] 超级管理员能否被现有数据**稳定识别**（见 §3.3 规则 4）。

## 3. 目标架构与边界

```text
HTTP 请求
  -> DTO 校验与转换
  -> AuthenticationGuard：解析凭证、校验会话、加载有效身份
  -> PermissionGuard：按路由元数据检查功能权限（默认拒绝）
  -> Controller：只做传输层编排
  -> Domain Service：用例、数据范围、授权边界、事务
  -> PrismaService / RedisConnection
```

### 3.1 代码归属与依赖方向

```text
apps/gateway/src/modules/
├── auth/                  # 登录、登出、当前用户/权限查询、会话与权限快照服务、Guard 实现
└── system/
    ├── user/              # 用户业务、用户-角色/部门关联
    ├── role/              # 角色业务、角色-菜单/部门授权
    ├── menu/              # 菜单树与权限标识管理
    └── dept/              # 部门树与数据范围支持

libs/core/src/decorators/  # 仅授权元数据装饰器与类型/注入令牌（不依赖业务模块）
```

**依赖倒置（重要）**：`libs/*` 不得导入 `apps/*`，也不应直接依赖 Prisma/Redis 的业务查询。

- `libs/core` 只放：`@Public()`、`@RequirePermissions()`、`CurrentUser` 参数装饰器、`AuthContext` 类型、`PERMISSION_RESOLVER` 等注入令牌。
- **Guard 的具体实现放在 `auth` 模块**，通过令牌获取权限解析器，避免平台库反向依赖业务。
- 权限标识匹配函数（纯函数、无 Nest/DB 依赖）：确有跨模块复用时才独立成库，否则放在 `auth` 模块内部。
- 数据库查询与 RBAC 策略归业务模块，不塞入 `DatabaseService`。跨模块协作用**导出的窄服务接口**，不直接查他人表，不产生循环依赖。

### 3.2 认证、功能授权、数据授权

| 层次     | 回答的问题     | 责任方                | 关键约束                                       |
| -------- | -------------- | --------------------- | ---------------------------------------------- |
| 认证     | 是谁           | `AuthenticationGuard` | 客户端传来的 userId/roleKey/权限列表一律不可信 |
| 功能授权 | 能做什么操作   | `PermissionGuard`     | 比对路由声明的 `perms`，默认拒绝               |
| 数据授权 | 能操作哪些记录 | Domain Service        | 功能权限通过 ≠ 数据范围通过                    |
| 菜单呈现 | 界面显示什么   | 菜单树/按钮权限       | **仅 UI 用途，不是 API 安全边界**              |

### 3.3 权限规则

1. **状态有效性**：用户必须存在、未软删除且状态有效；分配给用户的角色同样必须未软删除且有效。无效角色从有效集合剔除；用户无效则整体拒绝。需分别测试「认证场景」与「授权场景」。
2. **权限聚合**：有效角色的 `RoleMenu` 汇总得到 `Menu.perms`；忽略无效/已删除菜单与空权限标识；多角色取**并集**。聚合应为**单次（或常数次）查询**，禁止按角色/菜单逐条循环查询（N+1）。
3. **权限标识与匹配**：
   - 格式 `domain:resource:action`（如 `system:user:list`），与 `Menu.perms` 精确对应，匹配前统一 trim，**区分大小写**。
   - 仅支持受控的**段级通配**（如 `system:user:*`、`system:*:*`），严禁子串/正则匹配；单独的 `*` 不得被普通角色授予，仅超管规则可用。
   - 声明语义：`@RequirePermissions('a', 'b')` 默认「全部满足（AND）」，需要「任一满足」时用显式选项 `{ mode: 'any' }`。
   - 实现建议：快照内预拆分为 `Set` 精确集合 + 通配前缀集合，匹配为 O(1) 精确 + O(段数) 通配。
4. **超级管理员**：绕过规则只有在「现有数据可稳定识别 + 有审计与测试」时才启用。识别方式必须来自已确认的数据事实（如经核对的 `roleKey`，并通过配置项注入），**禁止硬编码未确认的用户名或 ID**。无法稳定识别则本期不实现超管绕过，上报为数据模型决策。
5. **菜单树**：只返回用户有权访问的目录/菜单，并**补齐父级路径所需节点**；按钮权限不伪装成导航节点；输出按 `orderNum`（以实际字段为准）稳定排序；对环形引用做防御。
6. **权限快照内容**：至少包含 `userId`、`roleKeys`、权限标识集合、数据范围元信息（角色 `dataScope` 与自定义部门 ID 集合、所属部门 ID）、`epoch`、`issuedAt`。**不得缓存**密码、令牌明文或不必要的个人信息。
7. **缓存只为性能**：数据库/身份校验规则仍是权威。失效策略不完整时，宁可缩短 TTL 或回源，不得依赖长时间陈旧快照做安全授权。
8. **防权限提升（授权类写操作必守）**：
   - 操作者只能向用户/角色授予**自己已拥有**的角色或权限（子集原则）。
   - 禁止修改**自己**的角色/权限绑定。
   - 保护「最后一个可管理授权的账号/角色」不被删除、停用或剥离权限。
   - 删除/停用角色、菜单、部门前，检查并处理关联影响（拒绝或明确级联策略），行为必须有测试。
9. **数据范围语义**（取值以 §2.3 核对结果为准）：
   - 多角色按**并集**（范围最宽者生效）；`全部` 直接短路为无限制。
   - `自定义`：取 `RoleDept` 部门集合；`本部门`：用户 `deptId`；`本部门及以下`：基于 `ancestors` 路径匹配，**必须带分隔符边界**，避免 `1` 误匹配 `10`；`仅本人`：按创建者/所有者字段（以业务表实际字段为准）。
   - 用户无部门（`deptId` 为空）时，需要部门的范围**收缩为仅本人或空集**，不得退化为全部。
   - 数据范围必须作用于：列表、详情、更新、删除、导出、批量操作。仅过滤列表会形成 IDOR。
   - 无权访问的单条记录，对外统一返回 **404**（避免泄露存在性）；功能权限不足返回 **403**。

### 3.4 凭证、会话与 Redis 约束

**凭证形态**：服务端生成 256 位随机不透明令牌；Redis 仅存其 **SHA-256 摘要**作为键（泄露 Redis 不等于泄露可用令牌）。

**会话数据**（Redis，TTL）：`userId`、`createdAt`、`lastActiveAt`、客户端元信息（UA 摘要/IP，可选）、会话授权纪元。

| 项目     | 约定                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 有效期   | 绝对过期（如 8–12h）+ 滑动空闲过期（如 30min），数值走配置，不硬编码                        |
| 传输     | 默认 `Authorization: Bearer`；若采用 Cookie 则必须 `HttpOnly; Secure; SameSite` 并评估 CSRF |
| 登出     | 删除当前会话；支持「登出所有设备」                                                          |
| 用户索引 | `userId → 会话集合` 反向索引，用于禁用用户、重置密码、改角色时批量吊销                      |
| 刷新令牌 | **本期不做**（无持久化表）；需要「长期免登录」列为后续数据模型决策                          |

**Redis 键规划**（统一前缀，如 `rbac:`）

| 键                                | 用途                 | TTL             |
| --------------------------------- | -------------------- | --------------- |
| `rbac:sess:{sha256(token)}`       | 会话                 | 绝对 + 滑动     |
| `rbac:user-sess:{userId}`         | 用户会话索引（Set）  | 与最长会话一致  |
| `rbac:snap:{userId}`              | 权限快照             | 短（如 1–5min） |
| `rbac:epoch`                      | 全局授权纪元（INCR） | 无              |
| `rbac:login-fail:{ip}:{username}` | 登录限流计数         | 窗口期          |

**失效策略（无「权限版本字段」下的方案）**

- 角色/菜单/部门/用户-角色/角色-菜单任何授权相关写操作成功后，`INCR rbac:epoch`，并清理受影响用户快照。
- 每次请求读取快照时比对 `snapshot.epoch === 当前 epoch`，不一致则回源重建。代价是每请求一次 Redis 读取，换取近实时生效，且逻辑简单可测。
- 用户被禁用/删除/重置密码：吊销该用户全部会话。

**失败关闭（强制）**

- 配置关闭 Redis 或启动时连接失败：认证模块**拒绝启动**或所有受保护路由返回 503/401，不得降级匿名。
- 运行时 Redis 异常：认证与授权**拒绝访问**（返回 503 或 401，按规范统一），记录告警日志，**不得**放行。
- 禁止通过通用 `CacheService` 读写会话或快照。

**登录安全（无锁定字段的替代方案）**

- 限流与失败计数放 Redis（按 IP + 用户名维度），超限返回统一错误并延迟，**不修改用户表**。
- 用户不存在时仍执行一次**等价耗时的哈希校验**（dummy hash），防止时序枚举。
- 错误信息统一为「用户名或密码错误」，不区分账号不存在/密码错误/已禁用（禁用可在内部日志区分）。
- 登录成功后若哈希参数过期，可在密码哈希服务支持下透明升级（有则做，无则不做）。

### 3.5 审计与可观测（无新表前提）

- 以**结构化日志**记录：登录成功/失败、登出、授权拒绝（403）、角色/权限变更、会话吊销、超管绕过命中。
- 日志含 `requestId`、`userId`、`action`、`result`，**不得包含**密码、令牌、完整快照。
- 指标建议：登录失败率、403 率、快照命中率、Redis 失败次数。持久化审计表属后续数据模型决策。

### 3.6 前端协作契约

- `GET /auth/me`：返回当前用户基本信息、`roleKeys`、权限标识集合（按钮级）与菜单树；字段走出参 DTO 白名单。
- **状态码语义**：`401` 未登录/会话失效 → 前端清状态并跳登录；`403` 已登录但无权限 → 前端提示，不跳登录；`404` 含「无数据范围」语义。
- 前端路由守卫与按钮指令（如 `v-permission`）只做体验优化；**每个接口必须独立受后端保护**。
- 权限变更感知：`/auth/me` 返回 `epoch` 或 ETag；前端在 403、窗口聚焦或定时拉取时刷新，避免「后端已撤权、界面仍显示」的长期漂移。
- 前端不得持久化权限快照作为授权依据（仅可缓存用于渲染）。

## 4. 分阶段实施计划

每阶段统一模板：**目标 / 范围 / 不做 / 验收 / 必备测试**。阶段间有依赖，**不得跳阶段**。

### 阶段 0：事实核对与前置条件

- **目标**：确认数据事实，补齐输入校验管线。
- **范围**：完成 §2.3 事实核对清单；按 ADR-009 落地全局/边界校验；确认 Redis 配置项与失败关闭策略；确定 Token 传输方式（Header/Cookie）。
- **不做**：任何认证、授权业务逻辑。
- **验收**：核对清单全部有结论；缺口已上报；无效 DTO 请求被校验管线拒绝。
- **必备测试**：校验管线对缺字段/类型错误/多余字段的行为测试。

### 阶段 1：认证与会话

- **目标**：登录、登出、会话校验、`AuthenticationGuard`、`@Public()`。
- **范围**：`PasswordHashService` 校验；会话服务（创建/校验/滑动续期/吊销/用户索引）；登录限流；`CurrentUser` 装饰器；全局默认启用认证（白名单显式 `@Public()`）。
- **不做**：权限快照、数据范围、管理接口。
- **验收**：未带凭证访问受保护路由 → 401；登出后令牌立即失效；禁用/删除用户后既有会话失效；Redis 不可用时受保护路由拒绝访问。
- **必备测试**：登录成功/失败/用户不存在（耗时近似）/已禁用；令牌篡改与过期；并发登出；Redis 故障模拟；日志不含敏感信息。

### 阶段 2：权限快照与功能授权

- **目标**：构建快照服务与 `PermissionGuard`。
- **范围**：权限聚合查询（单次）；快照读写 + epoch 校验；`@RequirePermissions()`（AND/ANY）；段级通配匹配纯函数；`GET /auth/me` 的权限部分。
- **不做**：菜单树、数据范围、授权写接口。
- **验收**：**未声明元数据的受保护路由默认拒绝**（防忘加装饰器）；多角色并集；无效角色/菜单被剔除；撤权后下一次请求即失效（epoch）。
- **必备测试**：匹配函数表驱动测试（精确、通配、边界、恶意输入如 `system:user` vs `system:users`、大小写、空串、`*`）；Guard 矩阵测试；缓存过期/epoch 变更/Redis 故障。

### 阶段 3：菜单树

- **目标**：按权限生成导航菜单树与按钮权限集合。
- **范围**：过滤、补齐父级、排序、环检测；`GET /auth/me` 菜单部分。
- **验收**：无权限目录不出现；有权限子菜单则父目录必出现；按钮不出现在导航树。
- **必备测试**：树构建的纯函数测试（孤儿节点、环、深层嵌套、禁用节点）。

### 阶段 4：数据范围

- **目标**：统一的数据范围 where 构造能力。
- **范围**：`DataScopeService`（窄接口，返回 Prisma where 片段）；部门子树解析（带分隔符边界）；多角色并集；无部门收缩；在 `user` 模块作为首个落地点，覆盖读/改/删。
- **不做**：给所有业务表一次性接入（按模块逐步接入）。
- **验收**：各范围类型在列表、详情、更新、删除上结果一致；越权详情返回 404。
- **必备测试**：部门树夹具（含 `1`/`10`/`11` 前缀陷阱）；每种 `dataScope` × 每种操作的矩阵；多角色并集；无部门用户。

### 阶段 5：管理接口与防提升

- **目标**：用户/角色/菜单/部门管理闭环，满足 §3.3 规则 8。
- **范围**：CRUD + 关联授权；子集授予校验；禁改自身授权；最后管理员保护；每次授权写后 `INCR epoch` 并吊销必要会话；密码创建/重置走哈希服务。
- **验收**：普通管理员无法授予超出自身的权限；删除/停用有引用时行为符合约定。
- **必备测试**：提权尝试的负向用例集；事务与回滚；epoch 与会话吊销副作用。

### 阶段 6：加固与文档

- **目标**：安全回归、性能与文档同步。
- **范围**：端到端权限矩阵；快照命中率与查询次数核查；更新 `docs/项目文件地图与架构说明.md`；整理遗留数据模型决策清单。
- **验收**：全量测试实际输出附在汇报；文档与代码事实一致。

## 5. 测试策略（TDD 与自动化）

| 层级         | 对象                                                  | 策略                                                          |
| ------------ | ----------------------------------------------------- | ------------------------------------------------------------- |
| 单元（先写） | 权限匹配、菜单树构建、数据范围 where 构造、epoch 判断 | 纯函数，表驱动，**先写测试后实现**                            |
| 集成         | Guard、会话服务、快照服务、Service 数据范围           | 真实 Postgres/Redis（测试容器或测试库），不 mock 核心权威逻辑 |
| 端到端       | 登录 → 访问 → 撤权 → 再访问                           | 覆盖 401/403/404 三种语义                                     |
| 安全回归     | 提权、IDOR、令牌篡改、时序、Redis 故障                | 每个已修复缺陷落一条回归用例                                  |

**权限矩阵测试**：`{角色组合} × {接口} × {期望结果}` 用数据驱动生成，新增接口时必须新增一行，CI 中缺失即失败。

**CI 门禁建议**：类型检查、Lint、全量测试、「所有路由必须声明 `@Public()` 或 `@RequirePermissions()`」的路由扫描测试。

## 6. 性能与可扩展性

- 请求热路径预算：**Redis 读 ≤ 2 次**（会话 + 快照/epoch），数据库 0 次（命中时）。
- 快照重建：一次聚合查询取得角色 + 权限 + 数据范围元信息，禁止循环查询。
- 部门子树：一次查询取出 `ancestors` 匹配的部门 ID 集合，再用 `deptId IN (...)` 过滤，避免在业务查询里做字符串模糊匹配。
- 大权限集合：快照用数组存储 + 内存构建 `Set`，注意序列化体积；超大时评估压缩。
- 水平扩展：会话与快照全部在 Redis，网关实例无状态；epoch 保证多实例一致。
- 若发现缺少必要索引：**记录证据（执行计划）并上报**，不得自行新增迁移。

## 9. 停止条件（命中即停并上报）

1. 需要新增/修改表、字段、索引、迁移或约束才能满足需求。
2. `status`/`delFlag`/`dataScope` 取值无法从 schema 与种子数据确定。
3. 超级管理员无法被现有数据稳定识别，但需求依赖其绕过。
4. 需要使用 `CacheService` 或任何「读失败即未命中」的路径承载会话/快照。
5. 需要让 `libs/*` 依赖 `apps/*`，或形成模块循环依赖。
6. 校验管线（阶段 0）未完成却要上线认证/管理接口。
