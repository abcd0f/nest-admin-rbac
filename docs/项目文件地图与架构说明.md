## 0. 一句话定位

一个 **NestJS 12 + Fastify 5 + Prisma 7 + PostgreSQL** 的纯后端网关工程，pnpm workspace 单仓多项目结构：`apps/gateway` 是唯一可运行的应用，`libs/*` 是 8 个可复用基础设施库，通过 `@app/*` 路径别名互相引用。

当前业务代码只有一个 `user` 模块，且 5 个接口里有 4 个是脚手架占位（返回字符串）。**基础设施是完整的、生产级的；业务层几乎是空的。** 接手时不要把 `libs/*` 当成半成品。

## 1. 技术栈与硬约束（先看这里，违反会直接编译失败）

| 项 | 值 | 说明 |
| --- | --- | --- |
| 运行时 | Node.js 22.22.0 | `.node-version` 固定 |
| 包管理 | pnpm（workspace） | `pnpm-workspace.yaml` 里 `shamefullyHoist: true`、`strictPeerDependencies: true`，registry 指向 npmmirror |
| 框架 | NestJS 12 | `@nestjs/platform-fastify`，**不是 Express** |
| HTTP | Fastify（`FastifyAdapter`） | 见第 4 节 |
| ORM | Prisma 7 + `@prisma/adapter-pg` | Prisma 7 无 Rust 引擎，**必须**用驱动适配器 |
| 数据库 | PostgreSQL | `prisma/models/*.prisma` 多文件 schema |
| 日志 | pino + nestjs-pino + pino-roll | 见第 9 节 |
| 缓存 | cache-manager 7 + Keyv + 自写 RedisStore | 见第 10 节 |
| 测试 | Vitest 4（不是 Jest） | `**/*.spec.ts` 单测、`**/*.e2e-spec.ts` e2e |
| Lint | ESLint 10 + `@antfu/eslint-config` | 2 空格、单引号、**必须带分号** |

### 1.1 三条最容易踩的硬约束

**① 严格 ESM：所有相对导入必须带 `.js` 后缀。**

`package.json` 有 `"type": "module"`，`tsconfig.json` 是 `module: nodenext`。所以：

```ts
import { UserService } from './user.service.js';   // ✅
import { UserService } from './user.service';      // ❌ 编译/运行都会失败
```

这不是风格问题，是 ESM 规范要求。`@app/*` 别名导入不用加后缀（走 tsconfig paths）。

**② 类型再导出必须写 `export type`。**

`isolatedModules: true`。`libs/*/src/index.ts` 里导出纯类型时用 `export type { XxxConfig }`，不能混在 `export { }` 里。

**③ 路径别名只有 `@app/*` 一套，且必须三处同步。**

新增一个 lib 时，以下三处都要改，漏一处就会出现「编译过、启动崩」：

1. `tsconfig.json` → `compilerOptions.paths`
2. `nest-cli.json` → `projects`
3. `libs/<name>/tsconfig.lib.json`（由 `nest g library` 生成）

## 3. 启动链路（main.ts 逐行）

`apps/gateway/src/main.ts` 只有 26 行，但它是理解全局的关键：

```ts
const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  createFastifyAdapter(),        // ← Fastify 在这里被创建，见第 4 节
  { bufferLogs: true },          // ← 日志先缓存，等 pino 就绪再吐
);
const logger = app.get(LoggerService);
app.useLogger(logger);           // ← 把 Nest 内置 Logger 桥接到 pino
app.enableShutdownHooks();       // ← 让 OnModuleDestroy / OnApplicationShutdown 生效
                                 //   （Prisma 断连、Redis 退出、pino flush 都靠它）

const configService = app.get(ConfigService);
const port = configService.get<number>('app.port', 3000);
app.setGlobalPrefix(configService.getOrThrow<string>('app.apiPrefix'));  // 默认 'api'
app.get(SwaggerService).setup(app);   // ← Swagger 在 listen 之前装配

await app.listen(port, '0.0.0.0');    // ← 绑定所有网卡
logger.log(`Application listening on ${await app.getUrl()}`);
```

**顺序依赖（不能随意调换）：**

1. `AppConfigModule.forRoot()` 必须在 `AppModule` 的 `imports[0]`。其它所有模块的 `forRootAsync` 都 `inject` 配置域的 token，配置没编译完就会抛 `配置域 X 尚未编译`。
2. `useLogger` 必须在任何业务日志之前，否则启动期日志走默认 ConsoleLogger，格式与运行期不一致。
3. `SwaggerService.setup(app)` 必须在 `listen` 之前（要拿 `app` 实例扫描路由）。
4. `enableShutdownHooks()` 是 Prisma / Redis / pino 三个组件能干净退出的前提，删掉它会泄漏连接。

**没有做的事（有意的空白，接手时注意）：**

- ❌ 没有 `app.enableCors()` —— 当前**没有任何 CORS 配置**。前端跨域需要自己加。
- ❌ 没有 `app.useGlobalPipes(new ValidationPipe(...))` —— 见第 14.1 节，这是当前最大的功能缺口。
- ❌ 没有 helmet / compression / cookie 等 Fastify 插件。

## 4. Fastify 怎么配（重点）

### 4.1 唯一的配置点

**文件：`libs/common/src/adapters/fastify.adapter.ts`（全文 12 行）**

```ts
export function createFastifyAdapter(): FastifyAdapter {
  const fastifyApp = new FastifyAdapter({
    trustProxy: true,   // 信任反向代理的 X-Forwarded-For，限流取 request.ip 才准
    logger: false,      // ❗必须 false：日志由 nestjs-pino 接管，开这里会双份日志
  });
  return fastifyApp;
}
```

设计意图：**把 Fastify 的构造选项集中到一个函数**，而不是散在 `main.ts` 里。测试里也复用同一个工厂（`test/app.e2e-spec.ts`、`test/cache.e2e-spec.ts`、`test/crypto.e2e-spec.ts` 都 import 它），保证测试环境与生产环境的 HTTP 层完全一致。

### 4.2 想加 Fastify 选项，改哪里

| 需求 | 改法 |
| --- | --- |
| 调大请求体上限 | 在 `new FastifyAdapter({ ... })` 里加 `bodyLimit: 10 * 1024 * 1024`。默认 1 MiB（1048576），加解密 hook 的限流阈值也读这个值 |
| 改连接超时 / keepAlive | 同上，加 `connectionTimeout`、`keepAliveTimeout` |
| 支持 HTTPS | 同上，加 `https: { key, cert }`（或用反向代理终止 TLS，本项目默认后者） |
| 自定义 404 / 错误处理 | 不要动 Fastify，用 `libs/core` 的 `AllExceptionsFilter`（已全局注册） |
| 注册 Fastify 插件（如 `@fastify/static`、`@fastify/compress`） | 见 4.4 |

### 4.3 Fastify 原生 hook（已装的两个）

`libs/crypto/src/fastify-api-crypto.ts` 通过 `ApiCryptoHooksInstaller` 在 `OnApplicationBootstrap` 阶段往 Fastify 实例上挂了两个 hook。**这是本项目唯一直接操作 Fastify 原生 API 的地方**，也是「报文加密」能工作的根本原因：

| Hook | 时机 | 干什么 |
| --- | --- | --- |
| `preParsing` | JSON 解析**之前** | 读 `encrypt-key` 头 → RSA 解出 AES key → AES-ECB 解密请求体 → 改 `content-type: application/json` → 把明文流交给后续解析器。失败返回 400（超限 413），直接 `reply.send` 一个标准错误体 |
| `onSend` | 响应写出**之前** | 若该路由 `@ApiEncrypt({ response: true })` → 生成临时 AES key → 加密响应体 → 把 RSA 加密后的 key 写回 `encrypt-key` 响应头 → 补 `Access-Control-Expose-Headers` |

必须在 `listen` 之前安装，否则 Fastify 的 hook 生命周期已启动，装不上。

### 4.4 如何注册一个 Fastify 插件

`NestFastifyApplication` 在 `listen` 之前可以直接 `register`：

```ts
// main.ts，在 app.listen 之前
await app.register(fastifyStatic, { root: join(process.cwd(), 'public'), prefix: '/static' });
```

注意：`@fastify/static` **已经装进了 dependencies 但代码里没有任何地方使用**（第 14 节列了这条）。要加静态资源服务时不需要再装包。

### 4.5 bodyLimit 的传递链

```
FastifyAdapter({ bodyLimit })            → fastify.initialConfig.bodyLimit
  ↓ 路由级可覆盖
request.routeOptions.bodyLimit
  ↓ 加解密 hook 里取
const maxBytes = request.routeOptions.bodyLimit ?? fastify.initialConfig.bodyLimit ?? 1048576;
```

解密时先累计字节数，超了直接抛 `body too large` → 413。**不要只改一处**：如果你在路由上单独设了 `bodyLimit`，解密阈值会跟着走，这是正确的；但如果你在 Fastify 构造里调大了，记得确认反向代理（Nginx `client_max_body_size`）也放开了。

## 5. 配置系统（第二复杂的一块）

### 5.1 三层 YAML 合并

```
config/default.yaml          基线层，所有环境共享，入库
  ↓ deep merge（对象递归合并，数组/标量直接覆盖）
config/<NODE_ENV>.yaml       环境差异层，入库，只写与基线不同的项
  ↓ deep merge
config/<NODE_ENV>.local.yaml 本地/部署层，❗不入库，放真实凭据
```

`NODE_ENV` 只接受 `development | test | production`（`libs/config/src/core/types.ts` 的 `ENVIRONMENTS`），其它值启动即抛错。默认 `development`。

`package.json` 里所有启动脚本都用 `cross-env NODE_ENV=xxx` 显式设置，**不读 `.env` 文件**（`ignoreEnvFile: true`、`skipProcessEnv: true`）。

### 5.2 加载与编译流程

```
loadConfigSource()                        libs/config/src/core/config-loader.ts
  ├─ resolveEnvironment()                 NODE_ENV → Environment
  ├─ 读 3 个 YAML，deepMerge
  └─ 返回 { environment, values }         （模块级缓存，configSource() 复用）

AppConfigModule.forRoot()                 libs/config/src/config.module.ts
  ├─ compileConfig(DOMAINS, snapshot)     libs/config/src/core/validate.ts
  │    └─ 逐个 domain.parse() + validate()，收集所有错误后一次性抛出
  │       错误格式：`配置校验失败：\n  - app.port: 必须是整数\n  - ...`
  └─ NestConfigModule.forRoot({ load: DOMAINS.map(d => d.token) })
       └─ 每个域通过 registerAs(namespace, ...) 注册成 ConfigService 的一个命名空间
```

**关键设计：启动时一次性校验全部配置，错误全量汇总。** 不是「用到才报错」，而是「配错就起不来」。这是有意的——线上配置错误宁可在启动时炸，也不要跑到第一个请求才炸。

### 5.3 七个配置域

全部在 `libs/config/src/domains/`，注册清单在 `domains/index.ts` 的 `DOMAINS` 数组（**新增域唯一需要改的清单**）。

| 域 | 文件 | 对应 YAML 节点 | 关键约束 |
| --- | --- | --- | --- |
| `app` | `app.domain.ts` | `app` | `port` ≥ 1；`api-prefix` 默认 `''` |
| `api-decrypt` | `api-decrypt.domain.ts` | `api-decrypt` | `enabled: true` 时**必须**同时有 private-key 和 public-key，否则启动失败 |
| `logger` | `logger.domain.ts` | `logger` | 控制台与文件**至少启用一个**；`size-mb`/`max-files` 必须正整数 |
| `swagger` | `swagger.domain.ts` | `swagger` | `enabled` 默认「非生产环境为 true」 |
| `throttler` | `throttler.domain.ts` | `throttler` | `ttl`/`limit` 正整数；`block-duration` 可选，`0` 表示不封禁 |
| `database` | `database.domain.ts` | `database` | `schema` 从 URL 的 `?schema=` 解析，缺省 `public` |
| `redis` | `redis.domain.ts` | `redis` | `key-prefix` 必须匹配 `/^[\w-]+(?::[\w-]+)*$/`；`port` 1..65535；`ttl` 1..2147483647（**禁止 0/永久**） |

### 5.4 怎么读配置（两种写法，都合法）

```ts
// 写法 A：注入域 token，拿到强类型对象（推荐，库内部都用这个）
constructor(@Inject(redisConfig.KEY) private readonly config: RedisConfig) {}

// 写法 B：用 Nest 的 ConfigService 按点路径取（只在 main.ts 用）
const port = configService.get<number>('app.port', 3000);
```

两种读的是同一份已编译对象。`ConfigService.get('app.port')` 能work是因为 `registerAs('app', ...)` 返回的对象被当作命名空间挂载了。

### 5.5 新增一个配置域的完整步骤

1. 新建 `libs/config/src/domains/<name>.domain.ts`：

```ts
export interface FooConfig { enabled: boolean; size: number; }

export const fooDomain = defineConfigDomain<FooConfig>({
  namespace: 'foo',                        // ← 必须与 YAML 顶层节点同名
  parse(raw): FooConfig {
    const value = asObject(raw, 'foo');
    return {
      enabled: asBoolean(value.enabled, 'foo.enabled', false),
      size: asInteger(value.size, 'foo.size', 10, 1),
    };
  },
});

export const fooConfig = fooDomain.token;  // ← 注入用的 token
```

2. `domains/index.ts` 里 import、加进 `DOMAINS` 数组、导出 `fooConfig` 和 `export type { FooConfig }`。
3. `config/default.yaml` 加 `foo:` 节点，**每一项都要写注释**（这是本仓库的强制约定）。
4. 用 `asXxx` 系列解析器（`core/parsers.ts`），不要手写 `typeof` 判断——它们统一负责报错文案和默认值。

`asXxx` 速查：`asString` / `asOptionalString` / `asBoolean` / `asInteger` / `asStrictInteger` / `asPositiveInteger` / `asEnum` / `asList` / `asOptionalList` / `asObject`。

`asInteger` 与 `asStrictInteger` 的区别：后者拒绝空白字符串和隐式类型转换（`Number('')===0`、`Number(true)===1`），凡是「被误转成 0 会造成严重后果」的字段（TTL、端口、限流次数）都用 `asStrictInteger`。

### 5.6 prisma.config.ts：绕开 Nest DI 的第二条配置入口

Prisma CLI（`prisma migrate` / `db push` / `studio`）不经过 Nest，所以 `prisma.config.ts` 直接调 `loadConfigSource()` 拿同一份 YAML 里的 `database.url`。**连接串只有一个来源**，不存在 schema 里写一份、代码里再写一份的情况。

代价：`prisma.config.ts` 在**项目根目录**执行，所以 `pnpm db:migrate` 必须在仓库根跑，`cd` 到别处会报 `缺少配置基线层`。

## 6. 请求生命周期（完整链路，按执行顺序）

```
① Fastify 收到连接
   └─ trustProxy: true 决定 request.ip

② preParsing hook（libs/crypto/src/fastify-api-crypto.ts）
   └─ 有 encrypt-key 头 → RSA+AES 解密请求体，改写为 application/json
      无 → 原样放行

③ Fastify JSON 解析

④ 全局守卫（APP_GUARD，按模块导入顺序执行）
   ├─ ApiEncryptGuard（CryptoModule）  @ApiEncrypt() 标注的路由缺 encrypt-key → 403
   └─ ThrottlerGuard（CoreModule）     按 IP+方法计数，超限 → 429

⑤ 管道（Pipe）
   └─ ❗当前没有任何全局 ValidationPipe，DTO 校验不会执行（见 14.1）

⑥ 控制器方法（apps/gateway/src/modules/system/**/*.controller.ts）
   └─ 调 Service

⑦ ResponseInterceptor（libs/core/src/interceptors/response.interceptor.ts）
   ├─ 有 @RawResponse() → 原样返回
   ├─ WebSocket / SSE   → 原样返回
   └─ 其余 → 包成 { code: 0, data: instanceToPlain(result), message: '操作成功' }
              注意 instanceToPlain 会触发 @EncryptField / @DateFormat 等 class-transformer 装饰器

⑧ onSend hook（libs/crypto/src/fastify-api-crypto.ts）
   └─ 路由声明了 response: true → 加密响应体，回写 encrypt-key 头

异常路径（任意阶段抛错）
   └─ AllExceptionsFilter（libs/core/src/filters/all-exceptions.filter.ts）
        ├─ BusinessException      → 保留 code + status + errors
        ├─ 其它 HttpException     → HTTP 状态映射业务码；5xx 一律用固定文案，不透传内部消息
        ├─ Prisma 错误（code 匹配 /^P\d{4}$/）→ 按 PRISMA_ERROR_HTTP_STATUS 映射
        │     P2002 → 409，P2025 → 404，P2024 → 503，其余 → 500
        └─ 未知错误 → 500 + 「系统内部错误」，原始堆栈只进日志
```

**两个必须记住的点：**

1. **响应体永远是这个形状**，没有例外（除非显式 `@RawResponse()`）：

```json
{ "code": 0, "data": { }, "message": "操作成功" }
{ "code": 404, "data": null, "message": "资源不存在" }
{ "code": 422, "data": null, "message": "请求参数校验失败", "errors": [{ "field": "pageSize", "messages": ["..."] }] }
```

2. **`code` 不是 HTTP 状态码的别名**：成功固定 `0`，通用错误码直接复用 HTTP 状态码数值，业务模块专属错误码从 `100001` 起分配（`libs/common/src/constants/business-code.ts` 里有明确说明，**不要往 BUSINESS_CODE 里加业务错误码**）。

## 7. 逐文件职责清单

### 7.1 `apps/gateway/src/`

| 文件 | 职责 | 备注 |
| --- | --- | --- |

## 8. 数据层

### 8.1 Prisma 7 的三个特殊点

1. **没有 Rust 引擎**。`generator client` 里 `engineType = "client"`，必须配驱动适配器 `@prisma/adapter-pg`（见 `prisma.service.ts`）。没有适配器 = 运行时直接报错。
2. **`datasource db` 故意不写 `url`**。连接串由 `prisma.config.ts` 在 CLI 侧提供，运行期由 `database` 配置域提供。**同一份 YAML，两个入口**。
3. **`schema` 必须走 `PrismaPg` 的第二个参数**。URL 上的 `?schema=` 只对 CLI 生效，运行期不认。

### 8.2 生成产物的路径

`prisma/schema.prisma` 里 `output = "../libs/database/src/generated/prisma"`，`moduleFormat = "esm"`、`generatedFileExtension = "ts"`、`importFileExtension = "js"`。

也就是说：**Prisma 直接生成 TS 源码**（不是 node_modules 里的 JS），编译期参与类型检查，产物导入带 `.js` 后缀。改完 `prisma/models/*.prisma` 必须跑 `pnpm db:generate`，否则类型不同步。

### 8.3 多文件 schema

`prisma.config.ts` 里 `schema: 'prisma/'` 指向目录，Prisma 会把 `prisma/models/*.prisma` 全部拼起来。当前只有 `user.prisma` 一个模型（`@@map("sys_user")`）。新增模型时在 `prisma/models/` 下加文件，**不要塞进 `schema.prisma`**（那个文件只放 generator 和 datasource）。

### 8.4 数据访问的三条分层约定

```
Controller → Service → (Repository) → PrismaService → PostgreSQL
```

- 业务查询直接用 `PrismaService` 的类型安全 API（`prisma.user.findMany()`），**不要**全塞进 `DatabaseService`。
- 需要跨模型事务时用 `DatabaseService.transaction(tx => ...)`，回调内必须用传入的 `tx`，否则语句不在同一事务里。
- Prisma 表达不了的复杂 SQL 用 `DatabaseService.raw` 模板字符串（自动参数化，别拼字符串）。

### 8.5 BigInt 与日期怎么处理

`User.userId` 是 `BigInt`，`createBy`/`updateBy` 也是。JSON.stringify 遇到 BigInt 会直接抛错。项目里的处理方式：

- **BigInt → 字符串**：出参 DTO 上加 `@Type(() => String)`。转换发生在 `toDto()` 的 `plainToInstance` 阶段，所以到 `instanceToPlain` 时已经是字符串了。
- **Date → 字符串**：出参 DTO 上加 `@DateFormat(undefined, { toClassOnly: true })`。`toClassOnly` 是因为转换在 `plainToInstance` 时发生，避免输出 JSON 时被再次按服务器时区解析。

新增出参 DTO 时这两个装饰器必须照抄，否则要么 500（BigInt），要么时区错 8 小时。

### 8.6 分页的正确用法

```ts
async findAll(query: QueryUserDto) {
  const data = await paginate(this.prisma.user, {
    ...query,
    where: { delFlag: '0' },        // 可选
  });
  return toPageDto(ResponseUserDto, data);   // ← 必须过一遍 DTO，否则 password 会泄露
}
```

`paginate` 返回的 `items` 是**原始 Prisma 对象**，包含 `password`。不过 `toPageDto` 是必须的，不是可选的——它靠 `excludeExtraneousValues: true` + `@Exclude()` 把密码剔掉。

## 9. 日志

- 统一 pino。业务代码注入 `PinoLogger`（`@app/logger`）或直接用 Nest 的 `Logger`（会被桥接）。
- 每条日志自动带 Fastify 的 `req.id`，跨 `await` 也能关联（e2e 专门测了这个）。
- **脱敏是默认的**：`password`、`token`、`accessToken`、`refreshToken`、`authorization`、`cookie` 及其一层嵌套同名键 → `[REDACTED]`。查询串在 `req` 序列化时就被截掉（`url.split('?')[0]`）。
- 级别策略：5xx 和带 err → `error`；4xx → `warn`；其余 `info`。
- 输出：控制台（开发环境 pretty、生产 JSON）+ `logs/gateway/gateway.log`（全量）+ `logs/gateway/error.log`（仅 error）。轮转按 `size-mb` 和 `frequency` 双条件，`max-files` 含活动文件。
- **每个进程必须独占日志目录**，多实例指向同一目录会互相删文件。

## 10. 缓存

- 默认**关闭**（`redis.enabled: false`）。关闭时 `RedisConnection.client` 是 `undefined`，`RedisStore.get` 返回 `undefined`、`set` 返回 `true`（**静默 no-op，看起来成功了但什么都没存**）。这是有意的降级，业务层不要依赖缓存做正确性保证。
- 开启后**连接失败会阻止启动**。这是明确的设计取舍：宁可起不来，也不要带着坏缓存跑。
- 故障期不排队（`enableOfflineQueue: false`）：读失败按未命中处理，写/删失败抛 `Redis 缓存命令执行失败`。
- `CacheService.clear()` 不存在（Store 的 `clear` 直接抛错）——**只能按业务键 `del`**，不允许批量清库。
- 缓存键最终形态：`<redis.key-prefix>:<业务键>`，例如 `nest-admin:cache:users:v1:42`。

## 11. 加解密（三个独立能力，别混）

| 能力 | 装饰器/服务 | 算法 | 用途 |
| --- | --- | --- | --- |
| API 报文加密 | `@ApiEncrypt()` + Fastify hooks | AES-ECB + RSA PKCS#1 v1.5 | 整包请求/响应，兼容 RuoYi-Vue-Plus |
| 字段级加密 | `@EncryptField()` / `@DecryptField()` | AES-256-GCM | 单个 DTO 字段落库/出参 |
| 密码哈希 | `PasswordHashService` | Argon2id | 用户密码，**不可逆** |

三者密钥体系完全独立，不要混用。协议细节全在 `libs/crypto/README.md`。

注意：`@ApiEncrypt()` 只对 **POST/PUT** 强制加密头；GET/DELETE 不会要求，但响应加密仍可通过 `response: true` 生效。

## 14. 已知问题与坑（接手前必读）

这些是**当前代码真实存在的缺口**，不是设计意图。改动相关代码时要么顺手修，要么明确绕开。

### 14.1 ❗没有全局 ValidationPipe —— DTO 校验完全不生效

`grep -rn "ValidationPipe" apps libs test` 结果为空。后果：

- `@Body() dto: CreateUserDto` 拿到的是**原始 plain object**，class-validator 装饰器不执行，`@Length(6,128)`、`@IsEmail()` 全是装饰。
- `@Type(() => Number)` 不执行，`?page=2` 到 service 时还是字符串 `'2'`。
- `PageQueryDto` 的默认值（`page = 1`、`pageSize = 20`）**在 HTTP 链路上不会生效**，只在 `plainToInstance` 显式调用时生效（单测里就是这样测的）。
- `@Transform` / `@DecryptField` 也不会触发。

`libs/crypto/README.md` 第 40 行也承认了这一点（「Nest 的 `@Body()` 默认不会自动将请求对象转换成此 DTO」）。

修复方式（`main.ts` 里加）：

```ts
app.useGlobalPipes(new ValidationPipe({
  transform: true,
  whitelist: true,
  forbidNonWhitelisted: true,
  transformOptions: { enableImplicitConversion: false },
  exceptionFactory: (errors) => BusinessException.validation(flatten(errors)),
}));
```

注意 `exceptionFactory` 要拍平成 `FieldError[]`（`BusinessException.validation` 已备好接口）。**没有现成的 flatten 工具**，需要自己写或从 `libs/core/src/pipes/` 补一个。

### 14.2 `libs/common` 与 `libs/core` 存在包级循环引用

- `libs/common/src/dto/base.dto.ts` → `import { DateFormat } from '@app/core/decorators/index.js'`
- `libs/core/src/core.module.ts` / `exceptions/business.exception.ts` / `filters/all-exceptions.filter.ts` → `import ... from '@app/common/constants/index.js'`

运行时不会炸（两边导入的是不同文件，没有真实环），但包依赖是双向的。想彻底解决，把 `DateFormat` 下沉到 `common`，或把 `constants` 提到独立包。**新增代码不要再加剧这个方向**。

### 14.3 `user.controller.ts` 有一行空导入

```ts
import {} from './dto/response.dto.js';
```

残留代码。作用可能是为了让 `ResponseUserDto` 参与 Swagger 扫描，但它被 `@Body()`/返回值类型引用了吗？没有。可以删。

### 14.4 `SystemModule` 标了 `@Global()`

`@Global()` 在业务模块上意味着 UserModule 的 provider 全局可见。这会让依赖关系隐式化，后续加 dept/role/menu 时容易出现「不知道谁依赖谁」。建议只保留 `DatabaseModule` / `ConfigModule` / `CryptoModule` 这类真正的基础设施为 Global。

### 14.5 `format` 脚本的 glob 少一个引号

```json
"format": "prettier --write \"apps/**/*.{ts,js} libs/**/*.{ts,js}\""
```

两个 glob 被包进同一个字符串了，Prettier 会当成一个非法 pattern。要么拆成两个参数，要么改 `apps/**/*.{ts,js}` `libs/**/*.{ts,js}` 分开写。

### 14.6 `FIELD_ENCRYPTION_KEY` 硬编码在源码里

`libs/common/src/constants/field-encryption.ts` 里写死了密钥，值本身还带着 `change-in-production` 字样。任何拿到构建产物的人都能解密字段密文。上线前必须改成从配置域/密钥管理系统注入。

### 14.7 `prisma/migrations` 没有被 git 跟踪

`.gitignore` 里有一行 `migrations`（无路径限定），导致 `prisma/migrations/` 整个目录被忽略。`git ls-files prisma` 只返回两个 `.prisma` 文件，迁移 SQL 不在版本库里。

后果：换台机器 clone 下来，`pnpm db:deploy` 没有任何迁移可跑，数据库结构靠 `db:push` 猜。

修复：把 `.gitignore` 的 `migrations` 改成 `/migrations`（只忽略根目录），或删掉这行。

### 14.8 `@fastify/static` 装了但没用

`package.json` 的 dependencies 里有 `@fastify/static`，`grep` 全仓无引用。要么删依赖，要么等真需要静态资源时直接用（见 4.4）。

### 14.9 `redis.enabled` 默认值与文档描述不一致

`config/default.yaml` 里 `redis.enabled: false`，但 `docs/NestJS 企业级 RBAC...md` 第 111 行写的是「当前 `redis.enabled` 与 `api-decrypt.enabled` 均为 `true`」。以 **YAML 为准**：`redis` 关、`api-decrypt` 开。

注意 `api-decrypt.enabled: true` 且 `default.yaml` 里**放了真实的 RSA 公私钥**。这对密钥已经进版本库了，只能当开发密钥用，生产必须换。

### 14.10 限流是进程内内存计数

`ThrottlerGuard` 用默认内存存储，多实例部署时每个进程独立计数，总额度 = 单实例额度 × 实例数。要真正的全局限流，得实现基于 Redis 的 `ThrottlerStorage`（`docs/...架构设计...md` 的 3.5 节有方案）。

### 14.11 `trustProxy: true` 的安全前提

开了 `trustProxy` 意味着 `request.ip` 直接采信 `X-Forwarded-For`。如果网关**直接暴露在公网**（前面没有可信代理），客户端可以伪造这个头来绕过限流。部署时确保前面有 Nginx / SLB 覆盖该头。

## 15. 扩展手册（照着做，不会漏文件）

### 15.1 新增一个业务模块（以 `role` 为例）

```
apps/gateway/src/modules/system/role/
├── role.module.ts
├── role.controller.ts
├── role.service.ts
└── dto/
    ├── role.dto.ts          ← 必须以 .dto.ts 结尾（Swagger 插件要求）
    └── response.dto.ts
```

1. 新建 4 个文件（相对导入全部带 `.js`）。
2. `role.module.ts` 里 `@Module({ controllers: [RoleController], providers: [RoleService], exports: [RoleService] })`。**不需要 import DatabaseModule**（它已 `@Global()`）。
3. `system.module.ts` 的 `imports` 加 `RoleModule`。
4. Controller 路径自动拼上全局前缀：`@Controller('role')` → `/api/role`。
5. 出参 DTO 照 `ResponseUserDto` 抄：每个字段 `@Expose()`，BigInt 用 `@Type(() => String)`，日期用 `@DateFormat(undefined, { toClassOnly: true })`，敏感字段 `@Exclude() + @ApiHideProperty()`。
6. 列表接口用 `paginate()` + `toPageDto()`。
7. 需要专属错误码时，在模块内建 `role.error.ts`，从 `100201` 起分配（`1001xx` 给 user，`1002xx` 给 role），用 `satisfies BusinessErrorDefinition` 约束。

### 15.2 新增一个 lib

```bash
pnpm exec nest g library mylib    # 生成 libs/mylib + tsconfig.lib.json + 自动改 tsconfig.json/nest-cli.json
```

生成后手动确认三处都已更新（1.1 节的硬约束③），再在 `libs/mylib/src/index.ts` 里导出公共 API。

### 15.3 新增一个模型

1. `prisma/models/<name>.prisma` 新建 `model`，加 `@@map("sys_xxx")`。
2. `pnpm db:generate`。
3. `pnpm db:migrate --name add_xxx`（在仓库根跑）。
4. ⚠️ 迁移文件不会进 git（14.7），手动 `git add -f prisma/migrations/` 或先修 `.gitignore`。

### 15.4 新增一个全局增强器（Guard/Interceptor/Filter/Pipe）

**只改 `libs/core/src/core.module.ts` 的 `providers`**，用 `APP_GUARD` / `APP_INTERCEPTOR` / `APP_FILTER` / `APP_PIPE` 令牌注册。不要在 `main.ts` 里 `useGlobalXxx()`——那样做拿不到 DI，也无法在测试里替换。

### 15.5 需要跳过统一响应包装

方法或控制器上加 `@RawResponse()`（`@app/core`）。适用：文件下载、流式响应、第三方回调要求的固定格式。
