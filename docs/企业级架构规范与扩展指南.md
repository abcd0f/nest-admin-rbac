## 1. 架构总纲

### 1.1 架构风格

**模块化单体（Modular Monolith）+ 库化平台层（Internal Platform Libs）。**

一句话概括：**一个可执行进程，8 个基础设施库，N 个业务模块，通过路径别名在编译期完成边界约束。**

```text
                    ┌──────────────────────────────────────┐
                    │        单一可执行进程 gateway         │
                    │                                      │
   HTTP ──────────► │  ┌────────┐  ┌────────┐  ┌────────┐ │
   (Fastify)        │  │ system │  │ 待扩展  │  │ 待扩展  │ │  ← L3 领域模块
                    │  │  user  │  │  role  │  │  dept  │ │
                    │  └───┬────┘  └───┬────┘  └───┬────┘ │
                    └──────┼───────────┼───────────┼──────┘
                           └───────────┴───────────┘
                                       │
                    ┌──────────────────▼───────────────────┐
                    │      L2 平台层（libs/*，8 个库）       │
                    │  config core common database cache   │
                    │  crypto logger swagger               │
                    └──────────────────┬───────────────────┘
                                       │
                    ┌──────────────────▼───────────────────┐
                    │      L1 数据契约（prisma/）           │
                    │  PostgreSQL + Prisma 7 Client        │
                    └──────────────────────────────────────┘
```

### 1.2 为什么是单体而不是微服务

| 维度 | 当前选择 | 理由 |
| --- | --- | --- |
| 部署单元 | 1 个进程 | 团队规模与业务体量不支持微服务的运维成本；RBAC 是典型的强内聚域，拆开只会制造分布式事务 |
| 模块边界 | 编译期（路径别名 + 目录） | 未来要拆服务时，`modules/<domain>` 目录即服务边界，`libs/*` 即共享内核，拆分成本可控 |
| 数据库 | 单一 PostgreSQL | 跨模块 JOIN 是权限系统的刚需（用户-角色-菜单），拆库会让「权限快照」变成 N 次远程调用 |
| 缓存 | 单一 Redis 连接 | 会话、权限快照、限流共用，见 `RBAC 文档` 3.5 节 |

**这不是「以后要拆微服务」的过渡态，而是一个明确的终态选择。** 只有在出现独立伸缩需求（例如报表服务、文件服务）时才拆，拆的时候把 `modules/<x>` 连同它的表一起搬走。

### 1.3 质量属性优先级

设计冲突时按此顺序裁决：

1. **正确性** —— 权限、金额、状态机相关的错误不可接受。宁可不做，不可做错。
2. **安全性** —— 默认拒绝、最小暴露、密钥不落库不入日志。
3. **可观测性** —— 出问题必须能在 5 分钟内定位到「哪个请求、哪个模块、哪条 SQL」。
4. **可测试性** —— 无法测试的设计视为设计缺陷。
5. **可扩展性** —— 新增一个业务模块不应该改动任何平台库。
6. **性能** —— 在满足 1-5 的前提下优化；不做无度量的优化。

### 1.4 架构不变式（Invariants）

以下 7 条是**不可协商**的，任何改动违反即视为架构破坏：

| # | 不变式 | 违反后果 |
| --- | --- | --- |
| I1 | 依赖只能从上层指向下层，`libs` 永不 import `apps` | 平台库被业务污染，无法复用、无法单测 |
| I2 | 所有 HTTP 出参经过 Response DTO 白名单过滤 | 密码、内部 ID、软删标记泄露 |
| I3 | 所有 HTTP 响应（成功/失败）符合统一信封 | 前端契约崩坏，错误处理失效 |
| I4 | 配置只在启动时读取并校验一次，运行期不可变 | 行为不可预测，无法复现问题 |
| I5 | 业务错误用 `BusinessException` 携带稳定业务码 | 客户端无法按码分支，错误不可观测 |
| I6 | 每个请求都有可关联的 `req.id`，日志不含凭据 | 排障靠猜，日志成为泄露源 |
| I7 | 数据访问只经 `PrismaService`，禁止字符串拼接 SQL | SQL 注入 |

## 2. 四层模型

### 2.1 层次定义

| 层 | 名称 | 物理位置 | 职责 | 允许知道的 |
| --- | --- | --- | --- | --- |
| **L4** | 接入与装配层 | `apps/gateway/src/main.ts`、`app.module.ts`、`libs/common/src/adapters/` | 创建进程、装配模块、注册全局增强器、安装 Fastify hook | 所有下层 |
| **L3** | 领域模块层 | `apps/gateway/src/modules/**` | 业务规则、用例编排、事务边界、DTO 转换 | L2、L1 |
| **L2** | 平台能力层 | `libs/*` | 配置、日志、错误、响应、缓存、加密、数据访问、文档 | 同层（按 3.2 方向）、L1 |
| **L1** | 数据契约层 | `prisma/`、`libs/database/src/generated/` | 表结构、约束、索引、生成客户端 | 无（最底层） |

### 2.2 L2 内部再分三类

平台层不是平的，8 个库有三种角色，**混用角色是常见的架构腐化起点**：

```text
┌─ 内核库（Kernel）────────────────────────────────────┐
│  common     零依赖的纯工具：常量、正则、分页 DTO、adapter  │
│  config     配置加载与校验，所有库的输入源                 │
└──────────────────────────────────────────────────────┘
┌─ 基础能力库（Capability）─────────────────────────────┐
│  core       HTTP 语义：响应包装、异常映射、限流、装饰器     │
│  database   持久化：Prisma 客户端、事务、分页 helper       │
│  cache      缓存：Redis 连接、Keyv Store、CacheService    │
│  crypto     密码学：报文加密、字段加密、密码哈希            │
│  logger     日志：pino 配置、多目标、轮转                  │
│  swagger    文档：OpenAPI 装配                            │
└──────────────────────────────────────────────────────┘
```

- **内核库**：只提供数据结构和纯函数，不含 I/O，不含 Nest 生命周期。可以在任何地方被 import。
- **能力库**：含 I/O 或框架集成，通过 Nest 模块暴露 provider。

判断一个新库属于哪类：**有 I/O 或需要 DI 就是能力库，否则是内核库**。内核库不允许出现 `@Injectable()`。

### 2.3 L3 领域模块的内部结构

每个业务模块是**垂直切片**（vertical slice），内部再分四层：

```text
modules/system/user/
├── user.module.ts          ← 装配：controller + service + 导出的 provider
├── user.controller.ts      ← 传输层：只做「解包 HTTP → 调 service → 返回」
├── user.service.ts         ← 应用层：用例编排、事务边界、权限判断
├── user.repository.ts      ← 持久化层（可选，见 6.4）
├── user.error.ts           ← 领域错误定义（可选，见 6.5）
└── dto/
    ├── user.dto.ts         ← 入参 DTO（请求体）
    ├── user.query.ts       ← 查询 DTO（URL query）
    └── response.dto.ts     ← 出参 DTO（白名单）
```

**铁律：跨层数据必须变形。** Controller 拿到的是 Request DTO，Service 拿到的是 DTO 或领域对象，Repository 拿到的是查询条件，DB 返回的是 Prisma 模型，出站前必须转成 Response DTO。**任何一层都不允许把上一层的形状直接透传到下一层。**

## 3. 依赖规则（硬性）

### 3.1 全局方向

```text
L4 apps/gateway ──────────────┐
                              ▼
L3 modules/**  ──────────►  L2 libs/*  ──────────►  L1 prisma/
                              │
                              └── 同层内：common ← config ← {core, database, cache, crypto, logger, swagger}
```

**反向依赖是零容忍的**：`libs` 里出现 `import ... from '../../apps/...'` 或 `@app/gateway/*`，视为严重缺陷，必须重构。

### 3.2 库间依赖矩阵

行 = 依赖方，列 = 被依赖方。✅ 允许，⚠️ 受限/待整改，✗ 禁止。

| 依赖方 ↓ \ 被依赖 → | common | config | core | database | cache | crypto | logger | swagger |
| --- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **common** | — | ✗ | ⚠️¹ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **config** | ✅ | — | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **core** | ✅ | ✅ | — | ✗ | ✗ | ✗ | ✗ | ✗ |
| **database** | ✅ | ✅ | ✗ | — | ✗ | ✗ | ✗ | ✗ |
| **cache** | ✗ | ✅ | ✗ | ✗ | — | ✗ | ✗ | ✗ |
| **crypto** | ✅ | ✅ | ✗ | ✗ | ✗ | — | ✗ | ✗ |
| **logger** | ✗ | ✅ | ✗ | ✗ | ✗ | ✗ | — | ✗ |
| **swagger** | ✗ | ✅ | ✗ | ✗ | ✗ | ✗ | ✗ | — |

¹ **已知的架构债**：`libs/common/src/dto/base.dto.ts` 从 `@app/core/decorators` 取 `DateFormat`，形成 `common ↔ core` 包级环。运行时无害（导入的是具体文件，无真实环），但违反分层。整改方案见 17.2。

**推论：`common` 是最底层，它只能依赖自己。** 任何想让 `common` 依赖别人的需求，都是在提示「这段代码应该下沉到更低的库，或提到更上层」。

### 3.3 库间引用的写法

**库之间互相引用时用深路径，不用 barrel。**

```ts
// ✅ 库内部：只取需要的那一个模块，不拖入整个 barrel
import { REDIS_KEY_PREFIX_PATTERN } from '@app/common/constants/regex.js';
import { databaseConfig } from '@app/config';

// ⚠️ 库内部尽量避免：barrel 会把 dto → core 的依赖一起拉进来
import { BUSINESS_CODE } from '@app/common';

// ✅ 业务模块（L3）可以用 barrel，因为本来就要用一大片
import { PageQueryDto, toPageDto } from '@app/common';
```

原因：`@app/common` 的 barrel 会连带加载 `dto/base.dto.ts`，而后者又依赖 `@app/core`。在 `libs/config` 里用 barrel 会把 `core` 拖进依赖图，扩大耦合面。

### 3.4 业务模块之间的依赖

**默认禁止横向依赖。** 允许的唯一形式：模块 A 通过 `exports` 暴露 Service，模块 B 单向 import 模块 A 的 Module 并注入该 Service。

```ts
// role.module.ts
@Module({ controllers: [RoleController], providers: [RoleService], exports: [RoleService] })
export class RoleModule {}

// user.module.ts —— 单向：user → role
@Module({ imports: [RoleModule], controllers: [...], providers: [UserService] })
export class UserModule {}
```

硬性约束：
- **禁止双向**。`user → role` 且 `role → user` 就是环，Nest 会启动失败或需要 `forwardRef`。需要 `forwardRef` 的设计一律打回重做。
- **禁止直接 import 另一个模块的 DTO / Repository**。DTO 是模块的传输契约，跨模块要用**领域接口**（纯 TS interface，放在调用方模块的 `ports/` 或 `libs/common`）。
- **禁止跨模块直接查别人的表**。`UserService` 里写 `prisma.role.findMany()` 是越界——即使技术上能做到。表归属模块，查询必须走归属模块的 Service。

### 3.5 全局模块白名单

`@Global()` 会让依赖隐式化，只允许以下模块使用：

| 模块 | 是否 Global | 理由 |
| --- | :---: | --- |
| `AppConfigModule` | ✅ | 配置是所有模块的前置依赖，逐个 import 无意义 |
| `CryptoModule` | ✅ | 密码哈希、报文加密是普适能力，且内部注册了全局 Guard |
| `DatabaseModule` | ✅ | 数据访问是典型全局基础设施（`database.module.ts` 注释里有取舍说明） |
| `SystemModule` | ❌ **当前违规** | 业务模块不该 Global，会让 `UserService` 全局可见、依赖关系不可追踪。应去掉 `@Global()`，让 `AppModule` 显式 import |
| `LoggerModule` | ✅（框架决定） | nestjs-pino 自身标了全局，`PinoLogger` 可直接注入 |
| `CacheModule` | ❌ | 缓存是可选能力，业务模块**显式 import**，让「这个模块用缓存」成为显式事实 |
| `SwaggerModule` | ❌ | 只在 `main.ts` 用一次 |

### 3.6 路径别名规范

| 别名 | 指向 | 谁可以用 |
| --- | --- | --- |
| `@app/common` | `libs/common/src/index.ts` | 所有人 |
| `@app/config` | `libs/config/src/index.ts` | 所有人 |
| `@app/core` | `libs/core/src/index.ts` | 所有人 |
| `@app/database` | `libs/database/src/index.ts` | 所有人 |
| `@app/cache` | `libs/cache/src/index.ts` | 所有人 |
| `@app/crypto` | `libs/crypto/src/index.ts` | 所有人 |
| `@app/logger` | `libs/logger/src/index.ts` | 所有人 |
| `@app/swagger` | `libs/swagger/src/index.ts` | 仅 `main.ts` |

**禁止相对路径跨目录引用**：`import { X } from '../../../libs/common/...'` 一律禁止。相对路径只用于**同模块内部**。

## 4. 横切关注点落位

新增一个横切能力时，先查这张表：**已经有落位的不要另起炉灶**。

| 关注点 | 实现位置 | 业务层怎么用 | 禁止 |
| --- | --- | --- | --- |
| **配置读取** | `libs/config` | 注入域 token：`@Inject(redisConfig.KEY)` | 读 `process.env`、读 `process.cwd()` 拼路径 |
| **日志** | `libs/logger` | 注入 `PinoLogger` 或用 Nest `Logger` | `console.log`（lint 放开了但架构上禁止） |
| **错误抛出** | `libs/core/exceptions` | `throw new BusinessException(USER_NOT_FOUND)` | `throw new Error('用户不存在')` |
| **错误映射** | `libs/core/filters` | 已全局注册，无需干预 | 在 Controller 里 try/catch 后手写响应 |
| **响应包装** | `libs/core/interceptors` | 已全局注册，直接 `return data` | 手动拼 `{ code, data, message }` |
| **跳过包装** | `libs/core/decorators` | 方法/类上加 `@RawResponse()` | 在拦截器里加 if 判断具体路由 |
| **限流** | `libs/core/core.module.ts` | `@Throttle()` / `@SkipThrottle()` | 自己写计数器 |
| **入参校验** | ⚠️ **缺失**（见 16.7） | 当前无效 | 假设 DTO 装饰器会生效 |
| **报文加密** | `libs/crypto` | `@ApiEncrypt({ response })` | 在 Controller 里手写加解密 |
| **字段加密** | `libs/crypto` | DTO 字段加 `@EncryptField()` / `@DecryptField()` | 在 Service 里手动调 crypto |
| **密码哈希** | `libs/crypto` | 注入 `PasswordHashService` | 自己调 argon2 / bcrypt |
| **缓存** | `libs/cache` | 显式 import `CacheModule`，注入 `CacheService` | 自己 `new Redis()`（会绕过连接生命周期管理） |
| **事务** | `libs/database` | `DatabaseService.transaction(tx => ...)` | 在 Service 里 `$transaction` 散落多处 |
| **分页** | `libs/database/helpers` + `libs/common/dto` | `paginate()` + `toPageDto()` | 手写 `skip/take` 且不封顶 pageSize |
| **时间格式化** | `libs/core/decorators` | DTO 字段加 `@DateFormat()` | 在 Service 里 `dayjs().format()` 后返回字符串 |
| **业务码** | `libs/common/constants` | 通用码用 `BUSINESS_CODE`，业务码自建 | 往 `BUSINESS_CODE` 里加业务错误 |
| **API 文档** | `libs/swagger` + `nest-cli.json` 插件 | 写 JSDoc 注释 | 手写 `@ApiProperty()` / `@ApiOperation()` |
| **ID 生成** | ⚠️ 未统一 | 当前用数据库自增 | 应用层生成有序 ID（除非明确评估过） |

## 5. 请求管线与契约不变式

### 5.1 管线（不可重排）

```text
 ① TCP/TLS  ──► FastifyAdapter({ trustProxy, logger:false })
 ② preParsing hook ── 报文解密（libs/crypto/fastify-api-crypto.ts）
 ③ body parser ── JSON 解析
 ④ 全局 Guard ── ApiEncryptGuard（CryptoModule）→ ThrottlerGuard（CoreModule）
 ⑤ 全局 Pipe ── ⚠️ 当前为空
 ⑥ Controller ── 参数绑定
 ⑦ Service ── 业务编排 + 事务
 ⑧ ResponseInterceptor ── 统一信封 + instanceToPlain
 ⑨ onSend hook ── 响应加密
 ⑩ 异常任意阶段 → AllExceptionsFilter → 统一错误信封
```

**为什么 Guard 顺序有讲究**：`ApiEncryptGuard` 在 `ThrottlerGuard` 之前（`AppModule` 中 `CryptoModule` 先于 `CoreModule` 导入）。这意味着「未加密的请求」不会消耗限流额度。如果顺序反了，攻击者可以用大量未加密请求耗尽目标 IP 的额度，造成对其他正常请求的拒绝。

**注意**：这个顺序由模块导入顺序决定，是**实现细节而非框架契约**。如果业务上依赖这个顺序，必须写测试固定它（参考 `test/app.e2e-spec.ts` 的做法）。

### 5.2 响应信封（成功）

```json
{ "code": 0, "data": { }, "message": "操作成功" }
```

不变式：
- `code` 成功恒为 `0`，**不是 HTTP 状态码**。
- `data` 无返回值时为 `null`，**不是 `undefined`、不是 `{}`**。
- `message` 恒为字符串，中文，面向终端用户。
- 三个字段恒存在，顺序固定。

### 5.3 响应信封（失败）

```json
{ "code": 404, "data": null, "message": "资源不存在" }
{ "code": 422, "data": null, "message": "请求参数校验失败",
  "errors": [{ "field": "pageSize", "messages": ["pageSize 不能大于 200"] }] }
```

不变式：
- `data` 恒为 `null`。
- `errors` **仅在字段级校验失败时出现**，其余错误不带该字段（不要输出 `errors: []`）。
- `field` 是稳定路径表达式（`items.0.name`），不含 DTO 类名、不含原始输入值。
- 5xx **永不**透传内部异常消息，一律用 `DEFAULT_BUSINESS_MESSAGE` 里的固定文案。

### 5.4 业务码分段规划

`libs/common/src/constants/business-code.ts` 只放**通用码**（直接复用 HTTP 状态码 + `100000` 通用失败）。业务码按模块分段，**段位一旦分配不得复用**：

| 段位 | 归属 | 示例 |
| --- | --- | --- |
| `0` | 成功 | — |
| `400`–`599` | HTTP 语义映射（通用） | `404` 资源不存在 |
| `100000` | 通用业务失败 | — |
| `1001xx` | user | `100101` 用户不存在 |
| `1002xx` | role | `100201` 角色已被引用 |
| `1003xx` | dept | `100301` 部门存在子节点 |
| `1004xx` | menu | `100401` 菜单存在子节点 |
| `1005xx` | auth | `100501` 凭据错误 |
| `1006xx` | monitor / 日志 | `100601` 日志已归档 |
| `1007xx`–`1009xx` | 预留 | — |
| `2000xx+` | 跨模块编排错误 | `200001` 跨模块状态冲突 |

业务错误定义写法（每个模块一个 `*.error.ts`）：

```ts
// modules/system/user/user.error.ts
import type { BusinessErrorDefinition } from '@app/core';
import { HttpStatus } from '@nestjs/common';

export const USER_NOT_FOUND = {
  code: 100101,
  message: '用户不存在',
  status: HttpStatus.NOT_FOUND,
} as const satisfies BusinessErrorDefinition;

export const USER_ALREADY_DISABLED = {
  code: 100102,
  message: '用户已停用',
  status: HttpStatus.CONFLICT,
} as const satisfies BusinessErrorDefinition;
```

`as const satisfies` 是刻意的：`as const` 保住字面量类型，`satisfies` 做结构校验。少任何一个都会丢失类型安全。

### 5.5 契约演进规则

| 变更 | 允许 | 做法 |
| --- | --- | --- |
| 响应 `data` 新增字段 | ✅ | 直接加，前端忽略未知字段 |
| 响应 `data` 删除/改名/改类型 | ❌ | 新增字段 + 双写过渡 + 前端切换 + 下个版本删旧字段 |
| 请求新增必填字段 | ❌ | 先加可选 + 默认值，前端全部升级后再收紧 |
| 新增错误码 | ✅ | 从当前模块段位递增，**永不复用旧码** |
| 修改错误码含义 | ❌ | 新增码，旧码保留但不再抛出 |
| 修改信封结构 | ❌ | 不允许，包括字段顺序 |
| 新增 HTTP 状态码语义 | ⚠️ | 需先确认前端拦截器覆盖 |

**判据**：这个变更会不会让「上一版前端」出错？会，就是破坏性变更。

## 6. 业务模块设计规范

### 6.1 Controller 规范

Controller 是**传输适配器**，不是业务层。判定标准：**Controller 里出现 `if` 判断业务规则，就是错的。**

```ts
// ✅ 正确：解包 → 调用 → 返回
@Controller('user')
export class UserController {
  constructor(private readonly userService: UserService) {}

  /**
   * 分页查询用户
   * @remarks 支持按状态、部门筛选，默认按创建时间倒序。
   */
  @Get()
  findAll(@Query() query: QueryUserDto): Promise<PageResponseDto<ResponseUserDto>> {
    return this.userService.findAll(query);
  }
}
```

硬性规则：

| 规则 | 说明 |
| --- | --- |
| **返回值声明具体类型** | 必须写 `Promise<PageResponseDto<ResponseUserDto>>`，不能 `Promise<any>`。Swagger 插件靠它生成响应模型 |
| **不 try/catch** | 异常交给全局过滤器。`try/catch` 后重新抛会丢失堆栈，吞掉则违反 I5 |
| **不碰 Prisma** | Controller 里出现 `prisma` 就是越界 |
| **不拼响应体** | 直接 `return data`，拦截器负责包装 |
| **路由用复数资源名** | `@Controller('user')` 是现状，新模块建议 `users`（RESTful）。**同一模块内保持一致，不要混** |
| **HTTP 方法语义** | `GET` 查（幂等）、`POST` 建、`PUT` 全量改（幂等）、`PATCH` 局部改、`DELETE` 删（幂等） |
| **方法名** | `findAll` / `findOne` / `create` / `update` / `remove`，与 Nest CLI 脚手架一致 |
| **JSDoc 必写** | 方法注释生成 Swagger `summary`，`@remarks` 生成描述。这不是文档，是**接口契约的一部分** |

### 6.2 Service 规范

Service 是**用例编排层**，一个方法 = 一个用例。

```ts
// ✅ 正确
@Injectable()
export class UserService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly passwordHash: PasswordHashService,
  ) {}

  async create(dto: CreateUserDto): Promise<ResponseUserDto> {
    const exists = await this.prisma.user.findFirst({ where: { userName: dto.userName, delFlag: '0' } });
    if (exists) throw new BusinessException(USER_NAME_TAKEN);

    const user = await this.prisma.user.create({
      data: { ...dto, password: await this.passwordHash.hashPassword(dto.password) },
    });
    return toDto(ResponseUserDto, user)!;
  }
}
```

硬性规则：

| 规则 | 说明 |
| --- | --- |
| **不依赖 HTTP 类型** | 禁止注入 `@Req()`、`Request`、`Response`、`ExecutionContext`。Service 必须能在纯单测里调用 |
| **事务边界在这里** | 一次业务操作 = 一个事务。事务里只放写操作，外部 I/O（HTTP 调用、发消息）放事务外 |
| **出参转 DTO** | Service 返回 Response DTO，不返回 Prisma 模型。让「泄露密码」成为不可能，而不是靠评审发现 |
| **单方法 ≤ 30 行** | 超了就是缺一个私有方法或一个 Repository |
| **不做缓存决策** | 缓存放在 Service 外层（Decorator 或独立方法），不要在主流程里散落 `cache.get/set` |

### 6.3 DTO 三分类

| 类型 | 命名 | 位置 | 职责 |
| --- | --- | --- | --- |
| **Request DTO** | `CreateXxxDto` / `UpdateXxxDto` | `dto/xxx.dto.ts` | 请求体，class-validator 校验 + class-transformer 转换 |
| **Query DTO** | `QueryXxxDto extends PageQueryDto` | `dto/xxx.dto.ts` | URL query，天然带分页/排序 |
| **Response DTO** | `ResponseXxxDto` | `dto/response.dto.ts` | 出参白名单，每个字段 `@Expose()` |

**Response DTO 的四条铁律**（违反任意一条都会造成线上事故）：

```ts
export class ResponseUserDto {
  /** 用户id */
  @Expose()
  @Type(() => String)          // ① BigInt → string
  userId!: string;

  /** 创建时间 */
  @Expose()
  @DateFormat(undefined, { toClassOnly: true })   // ② Date → 字符串，固定 Asia/Shanghai
  createTime!: string;

  /** 密码 */
  @Exclude()                    // ③ 敏感字段显式排除
  @ApiHideProperty()            //    同时从 Swagger 隐藏
  password!: string;

  /** 备注 */
  @Expose()                     // ④ 每个要输出的字段都必须 @Expose()
  remark!: string | null;
}
```

为什么必须 `@Expose()`：`toDto()` 用了 `excludeExtraneousValues: true`，**没标 `@Expose()` 的字段会被静默丢弃**。这不是 bug，是白名单机制——它保证「新加的 Prisma 字段默认不泄露」。

为什么 `@DateFormat` 要 `toClassOnly: true`：转换在 `plainToInstance` 阶段完成，避免 `instanceToPlain` 输出 JSON 时被再次按服务器时区解析（会差 8 小时）。

### 6.4 何时引入 Repository

**默认不需要。** Service 直接用 `PrismaService` 是当前架构的既定选择，简单直接。

引入 Repository 的**唯一**触发条件：**同一段查询在 ≥3 个 Service 方法里重复，或需要被其他模块复用**。

```ts
// user.repository.ts —— 只在满足触发条件时创建
@Injectable()
export class UserRepository {
  constructor(private readonly prisma: PrismaService) {}

  findActiveByUserName(userName: string) {
    return this.prisma.user.findFirst({ where: { userName, delFlag: '0' } });
  }
}
```

**不要为了「架构好看」而给每个 Service 配一个 Repository。** 那会得到一层纯转发的空壳，增加 30% 代码量，零收益。`DatabaseService` 的注释里已经写明这个立场。

### 6.5 领域错误

每个模块一个 `*.error.ts`，用 `as const satisfies BusinessErrorDefinition`。**不要**在 Service 里内联错误对象，也不要复用别的模块的错误码。

跨模块场景：如果 A 模块需要「B 的某个东西不存在」，A 自己定义错误（`1001xx` 之外用 `2000xx` 段），不要 import B 的错误常量——那会制造模块间编译期耦合。

### 6.6 模块装配模板

```ts
// xxx.module.ts
import { Module } from '@nestjs/common';
import { XxxController } from './xxx.controller.js';
import { XxxService } from './xxx.service.js';

@Module({
  // 需要缓存时显式加 CacheModule（它不是全局的）
  // imports: [CacheModule],
  controllers: [XxxController],
  providers: [XxxService],
  exports: [XxxService],   // 只有确实要被其他模块调用时才导出
})
export class XxxModule {}
```

然后在 `apps/gateway/src/modules/system/system.module.ts` 的 `imports` 里加一行。

## 7. 配置架构

### 7.1 三权分立

| 内容 | 放哪 | 判据 |
| --- | --- | --- |
| **随环境变化的值** | `config/*.yaml` + 配置域 | 换环境要改 → 配置 |
| **永不变化的常量** | `libs/common/src/constants/` | 改了要重新发版且所有环境一致 → 常量 |
| **密钥** | `config/<env>.local.yaml`（不入库）或密钥管理系统 | 泄露有损失 → 密钥 |

**禁止**：`process.env.XXX` 直接读取（配置系统已 `skipProcessEnv: true`）、`.env` 文件（已 `ignoreEnvFile: true`）、在代码里 `if (process.env.NODE_ENV === 'production')` 分支。

需要区分环境行为时，用配置域的 `context.environment` 在 `parse()` 里决定默认值：

```ts
// ✅ 正确：默认值随环境变，但配置项本身是统一的
console: { pretty: asBoolean(console.pretty, 'logger.console.pretty', context.environment !== 'production') }
```

### 7.2 不可变与一次性校验

配置在 `AppConfigModule.forRoot()` 时**一次性编译**，之后是只读对象。

- **所有错误一次性汇总抛出**，不是「用到才炸」。配错就起不来，这是刻意的。
- 运行期**不存在**「重新加载配置」的能力。要改配置 = 重启进程。
- 测试里通过 `overrideProvider(xxxConfig.KEY)` 注入，不走 YAML。

### 7.3 新增配置项的判定流程

```text
需要一个新的可调参数？
  │
  ├─ 只影响一个平台库的行为？ → 加进该库对应的已有域（如 redis.*）
  ├─ 是一个新的能力域？       → 新建 domains/<name>.domain.ts + DOMAINS 数组
  ├─ 是业务模块的开关？       → 新建域（如 <module>.domain.ts），由该模块消费
  └─ 是纯常量？               → libs/common/src/constants/
```

**不要**把业务开关塞进 `app.*`。`app` 域只放进程级参数（port、api-prefix）。

### 7.4 YAML 编写规范

`config/default.yaml` 顶部已经写明约定，这里补充可执行的判据：

- 键名全小写 kebab-case（`api-prefix`、`log-queries`），**与最终 Config 对象的 camelCase 属性一一对应**（`api-prefix` → `apiPrefix`）。
- **每一项都必须有注释**，注释写「单位、取值范围、默认值、什么时候该改」。这是本仓库的强制约定，不是建议。
- 缺失的项走代码默认值；**不用的项直接删掉**，不要留 `# xxx: false` 的死配置。
- `default.yaml` 里**不允许出现真实凭据**（当前 `api-decrypt` 的密钥是违规的，见 10.4）。

## 8. 数据架构

### 8.1 Prisma 7 的三条特殊约束

| 约束 | 原因 | 违反后果 |
| --- | --- | --- |
| **必须用驱动适配器** `@prisma/adapter-pg` | Prisma 7 无 Rust 引擎，`engineType = "client"` | 运行时直接报错，无法连接 |
| **`datasource` 不写 `url`** | 连接串由 `prisma.config.ts`（CLI）+ 配置域（运行时）提供 | 连接串出现两个来源，环境切换失效 |
| **`schema` 走 `PrismaPg` 第二参数** | URL 上的 `?schema=` 只对 CLI 生效 | 运行期落到 `public`，查不到表 |

### 8.2 模型归属

| 文件 | 放什么 | 禁止 |
| --- | --- | --- |
| `prisma/schema.prisma` | **仅** generator + datasource | 放 model（当前只有 `User` 在 models/ 下，这是对的） |
| `prisma/models/<entity>.prisma` | 模型定义 | 跨实体关系写在谁的文件里？**写在「一对多」的多方**，或独立 `relations.prisma` |
| `prisma/migrations/` | 迁移 SQL | 手改已应用的迁移文件 |

命名约定（沿用当前 `user.prisma` 的做法）：

| 项 | 约定 | 示例 |
| --- | --- | --- |
| model 名 | PascalCase 单数 | `User`、`Role`、`Dept` |
| 表名 | `@@map` 成 `sys_` 前缀 + snake_case | `@@map("sys_user")` |
| 字段名 | camelCase，`@map` 成 snake_case | `@map("user_name")` |
| 主键 | `<entity>Id`，`BigInt @id @default(autoincrement())` | `userId` |
| 时间字段 | `Timestamptz(6)` | `@db.Timestamptz(6)` |
| 软删除 | `delFlag String @default("0") @db.Char(1)` | `'0'` 未删，`'2'` 已删 |
| 状态 | `status String @default("0") @db.Char(1)` | 与 RuoYi 保持一致 |
| 审计字段 | `createBy`/`createTime`/`updateBy`/`updateTime`/`remark` | `createBy` 用 BigInt |
| 字段注释 | `///` 三斜线（会进数据库注释） | `/// 用户名称` |

### 8.3 软删除与审计

当前**没有** Prisma 中间件或扩展自动处理软删除。这意味着：

- 每条查询都要显式写 `where: { delFlag: '0' }`。**漏写就是 bug。**
- 删除是 `update({ data: { delFlag: '2' } })`，不是 `delete`。
- 唯一索引要考虑软删除：`@@unique([userName, delFlag])` 而非 `@@unique([userName])`，否则删了不能再建同名。

**改进方向**（`RBAC 文档` 10 节已列）：在 `libs/database` 加 Prisma Client Extension 统一注入 `delFlag` 过滤，并把审计字段填充交给 Service 或扩展。落地前，显式写 `where` 是唯一正确做法。

### 8.4 迁移策略：Expand → Migrate → Contract

生产环境禁止破坏性单步迁移。三步走：

```text
① Expand   加新列（nullable 或带默认值）、加新表、加新索引（CONCURRENTLY）
            → 老代码仍能跑
② Migrate  双写/回填数据，切换读路径
            → 新旧代码都能跑
③ Contract 删旧列、删旧索引
            → 确认无回滚需求后再执行
```

硬性规则：
- **不删列、不改列类型**在同一个发布里完成。
- 大表加索引用 `CREATE INDEX CONCURRENTLY`（手写进迁移文件，Prisma 生成的普通 `CREATE INDEX` 会锁表）。
- 迁移文件**必须入库**（当前 `.gitignore` 有 bug，见 17.3）。

### 8.5 事务与并发

```ts
// ✅ 正确：事务里只用 tx，外部 I/O 放外面
await this.db.transaction(async (tx) => {
  await tx.userRole.deleteMany({ where: { userId } });
  await tx.userRole.createMany({ data: roleIds.map(roleId => ({ userId, roleId })) });
});
await this.cache.del(`auth:perm:${userId}`);   // 提交后再失效缓存
```

规则：
- 事务回调内**必须**用传入的 `tx`，用 `this.prisma` 会脱离事务。
- **缓存失效、消息发送、HTTP 调用放在事务提交后**。事务内做这些会导致「事务回滚但缓存已删」的不一致。
- 事务内禁止长耗时操作（事务会持有连接，`pool.max` 很快耗尽）。
- 并发更新用乐观锁（版本号）或 `updateMany` + 条件判断，不要「先查再改」。

### 8.6 查询规范

| 规则 | 原因 |
| --- | --- |
| 列表查询**必须**分页，走 `paginate()` | 无分页查询迟早拖垮数据库 |
| `paginate()` 的 `pageSize` 自动封顶 200 | `?pageSize=999999` 会打满连接池 |
| 只取需要的字段用 `select`，**不要** `select` 和 `omit` 同时用 | `paginate()` 会直接抛错 |
| 禁止 N+1：关联数据用 `include` 一次取 | 循环里 `await` 查询是性能杀手 |
| 原生 SQL 只走 `DatabaseService.raw` 模板字符串 | 自动参数化，防注入 |
| 生产环境 `log-queries: false` | SQL 日志含敏感数据且影响性能 |

## 9. 缓存架构

### 9.1 语义边界

`CacheService` 的定位是**可降级的业务缓存**，不是存储。它**不承担**：会话、授权、限流、唯一数据源。

| 用途 | 是否可用 CacheService | 应该用什么 |
| --- | --- | --- |
| 列表/详情的读缓存 | ✅ | `CacheService` |
| 字典、配置类低频变更数据 | ✅ | `CacheService` |
| 登录会话 | ❌ | 强一致 Redis 命令服务（待建） |
| 权限快照 | ❌ | 同上（需要版本号与原子失效） |
| 限流计数 | ❌ | `ThrottlerStorage` 适配器（待建） |
| 分布式锁 | ❌ | `SET NX PX` 原子命令服务（待建） |

原因：`CacheService` 的读失败会被降级为「未命中」，这对读缓存是优点，对会话校验是**致命的安全漏洞**（Redis 挂掉 = 所有人免认证）。

### 9.2 键命名空间

```text
nest-admin:cache:<业务域>:<版本>:<id>
  │          │        │         │       └─ 实体标识
  │          │         │         └─ 结构版本，schema 变更时递增，让旧缓存自然失效
  │          │         └─ 业务域（users、depts）
  │          └─ Keyv namespace（redis.key-prefix）
  └─ 平台根前缀
```

- `redis.key-prefix` 只用于**通用缓存**命名空间。
- 会话、权限、限流使用各自的根前缀（`nest-admin:auth:session:` 等），**不叠在 `cache:` 下面**。
- 键里**禁止**出现用户输入原文（防注入、防超长键）。需要时用哈希。

### 9.3 TTL 策略

| 数据类型 | TTL | 理由 |
| --- | --- | --- |
| 用户详情 | 5 分钟 | 变更不频繁，容忍 5 分钟不一致 |
| 字典/枚举 | 30 分钟 | 几乎不变 |
| 权限快照 | 30 分钟 + 版本号主动失效 | 被动过期太长，靠版本号兜底 |
| 会话 | = refresh 有效期 | 不能提前过期 |
| 限流计数 | = 限流窗口 | 由 throttler 管理 |

**禁止永久缓存**（`ttl: 0` 已被 `isValidCacheTtl` 拒绝）。永久缓存等于制造内存泄漏。

### 9.4 降级与失效

| 场景 | 行为 | 是否可接受 |
| --- | --- | --- |
| Redis 未启用 | 读写都是 no-op，`get` 返回 `undefined` | ✅ 业务必须能容忍 |
| 读失败（网络/超时） | 按未命中处理，回落数据库 | ✅ |
| 写失败 | 抛 `Redis 缓存命令执行失败` | ✅ 让调用方感知 |
| 启动时连不上 | **阻止启动** | ✅ 宁可起不来 |
| 批量清空 | 直接抛错 | ✅ 防误操作 |

**失效优先级**：主动删除 > TTL 过期 > 版本号变更。写操作后**立即删缓存**，不要「更新缓存」（并发下会写进旧值）。

## 10. 安全架构

### 10.1 分层防护

| 层 | 措施 | 现状 |
| --- | --- | --- |
| 传输 | HTTPS（反向代理终止） | ⚠️ 未强制，代码无 HSTS |
| 报文 | AES-ECB + RSA PKCS#1 v1.5（兼容 RuoYi） | ✅ `libs/crypto` |
| 字段 | AES-256-GCM（`enc:v1:` 前缀） | ✅ 但密钥硬编码（10.4） |
| 凭据 | Argon2id（m=64MiB, t=3, p=1） | ✅ |
| 认证 | JWT + Redis 会话 | ❌ 未实现（见 RBAC 文档 Phase 3） |
| 授权 | RBAC + 数据范围 | ❌ 未实现（Phase 4-8） |
| 限流 | 进程内计数 | ⚠️ 单实例有效 |
| 输入 | ValidationPipe 白名单 | ❌ **完全缺失**（16.7） |
| 输出 | Response DTO 白名单 | ✅ |
| 日志 | 字段脱敏 + URL 去 query | ✅ |
| 错误 | 5xx 不透传内部消息 | ✅ |

### 10.2 三种加密的边界

| 能力 | 算法 | 密钥来源 | 可逆 | 用途 |
| --- | --- | --- | --- | --- |
| 报文加密 | AES-ECB + RSA | `api-decrypt` 配置域 | ✅ | 传输层加固，防中间人抓包 |
| 字段加密 | AES-256-GCM | `FIELD_ENCRYPTION_KEY` 常量 | ✅ | 落库敏感字段（手机号、身份证） |
| 密码哈希 | Argon2id | 无（自带 salt） | ❌ | 密码校验 |

**禁止交叉使用**：不要用报文加密的 RSA 密钥做字段加密，不要把密码做可逆加密。

### 10.3 密钥管理规则

| 规则 | 说明 |
| --- | --- |
| 密钥只放 `config/<env>.local.yaml` 或密钥管理系统 | 该文件被 `.gitignore` 忽略 |
| 代码里不出现真实密钥 | 包括测试代码（测试用 `generateKeyPairSync` 现生成） |
| 密钥不进日志 | `logger.options.ts` 的 `REDACT_FIELDS` 已覆盖，新增敏感字段要同步加进去 |
| 密钥轮换要有迁移路径 | 字段加密的 `enc:v1:` 前缀就是为版本化留的 |
| 生产与开发密钥不同 | 泄露开发密钥不影响生产 |

### 10.4 当前安全债（必须在上线前清零）

| # | 问题 | 风险 | 处置 |
| --- | --- | --- | --- |
| S1 | `config/default.yaml` 里提交了真实 RSA 公私钥 | 报文加密形同虚设 | 换成占位符，真实密钥移入 `production.local.yaml` |
| S2 | `FIELD_ENCRYPTION_KEY` 硬编码在 `libs/common/src/constants/` | 拿到构建产物即可解密字段 | 移到配置域 + 密钥管理 |
| S3 | 无 ValidationPipe | 任意字段可注入，批量赋值漏洞 | 见 16.7 |
| S4 | 无认证 | 所有接口公开 | Phase 3 |
| S5 | `trustProxy: true` 但无前置代理约束 | 可伪造 `X-Forwarded-For` 绕过限流 | 部署层保证 |
| S6 | 无 CORS 配置 | 默认拒绝（相对安全），但前端无法跨域 | 需要时显式加白名单 |

## 11. 可观测性

### 11.1 三支柱现状

| 支柱 | 现状 | 缺口 |
| --- | --- | --- |
| **日志** | ✅ pino 结构化、双文件、脱敏、请求 ID 关联 | 无采样、无日志级别动态调整 |
| **指标** | ❌ 无 | 无 Prometheus / OpenTelemetry |
| **链路** | ⚠️ 单进程内靠 `req.id` 关联 | 无分布式追踪 |

### 11.2 日志规范

```ts
// ✅ 结构化字段，不拼字符串
this.logger.info({ userId, roleCount }, '权限快照已刷新');

// ❌ 拼字符串，无法检索
this.logger.info(`用户 ${userId} 的 ${roleCount} 个角色已刷新`);

// ❌ 泄露凭据（会被 redact 兜住，但不要依赖它）
this.logger.info({ password: dto.password }, '创建用户');
```

规则：
- **第一个参数是对象**（结构化上下文），**第二个是消息**。
- 消息用**英文短句 + 名词**，便于 grep（`HTTP request completed`、`Redis 缓存连接就绪`）。当前仓库中英混用，新代码建议统一英文消息 + 中文注释。
- 敏感字段加进 `REDACT_FIELDS`，不要指望调用方自觉。
- 错误日志传 `Error` 对象（走 `errWithCause` 序列化器拿到堆栈），不要只传 `error.message`。

### 11.3 健康检查（待建）

当前 `DatabaseService.health()` 已实现但**没有暴露成 HTTP 接口**。建议补齐两个端点：

| 端点 | 语义 | 内容 |
| --- | --- | --- |
| `GET /api/health` | 存活（liveness） | 进程活着就 200，不查依赖 |
| `GET /api/health/ready` | 就绪（readiness） | 查 PostgreSQL + Redis，任一不可用返回 503 |

两者都必须 `@RawResponse()` + `@SkipThrottle()`，且**不参与认证**。

## 12. 测试架构

### 12.1 测试金字塔

```text
        ╱╲          e2e（test/*.e2e-spec.ts）        ~10%
       ╱  ╲         真实 AppModule + 真实 PG/Redis
      ╱────╲
     ╱      ╲       集成（*.spec.ts，带 Nest TestingModule）  ~30%
    ╱        ╲      单个模块 + mock 外部依赖
   ╱──────────╲
  ╱            ╲    单元（*.spec.ts，纯函数/单类）      ~60%
 ╱______________╲   无 I/O、无 DI 容器
```

### 12.2 分层测试策略

| 被测对象 | 测试类型 | 关键点 |
| --- | --- | --- |
| 配置域 `parse()` | 单元 | 边界值（`0`、负数、`1.5`、`true`、`''`）、错误文案包含字段路径 |
| 纯函数（`matchPermission`、`normalizePage`） | 单元 | **必须 100% 分支覆盖**，这是权限系统的正确性基础 |
| Service | 集成 | mock `PrismaService` / `CacheService`，断言「调了什么、参数是什么」 |
| Controller | 集成 | 只测参数绑定与返回值形状，不测业务规则 |
| 全链路 | e2e | 真实启动 `AppModule`，断言响应信封、状态码、日志、副作用 |

### 12.3 测试替身规则

| 替身 | 允许 | 禁止 |
| --- | --- | --- |
| 配置 | `overrideProvider(xxxConfig.KEY).useValue(xxxDomain.parse({...}, ctx))` | 读真实 YAML（环境相关，不可重现） |
| 数据库 | e2e 用真实 PG（独立 schema/库） | 用 SQLite 模拟（类型系统不一致，测不出真问题） |
| Redis | `REDIS_TEST_URL` 指向独立实例 + 随机 `key-prefix` | 连开发环境的 Redis（污染数据） |
| 加密 | **独立实现**客户端（`test/helpers/api-crypto-client.ts`） | 复用服务端实现（两边同错则测不出） |
| 时间 | `vi.useFakeTimers()` | `sleep` 等待（慢且不稳定） |

### 12.4 e2e 的隔离要求

- 每个 e2e 文件用**独立的临时目录**做日志输出（`mkdtemp`），结束后删除。
- Redis 键前缀带 `randomUUID()`，结束后按前缀清理。
- 数据库用**独立 schema**，`beforeAll` 建、`afterAll` 删。
- 并发测试用 `Promise.all` + `vi.waitFor` 轮询断言，**不要** `setTimeout`。

### 12.5 必须写测试的场景（不可豁免）

1. 权限判定逻辑（`matchPermission`、数据范围构造）—— 安全边界。
2. 配置解析的边界值 —— 配错就起不来。
3. 统一响应/错误信封的形状 —— 前端契约。
4. 加密/解密的往返（round-trip）—— 错了就是数据损坏。
5. 事务回滚后的状态一致性 —— 错了就是脏数据。
6. Bug 修复 —— 先写复现测试，再修。

## 13. 代码风格与工程门禁

### 13.1 语言级硬约束

| 约束 | 原因 | 检查方式 |
| --- | --- | --- |
| 相对导入**必须**带 `.js` | 严格 ESM（`type: module` + `module: nodenext`） | `pnpm build` 会失败 |
| 纯类型导出用 `export type` | `isolatedModules: true` | tsc 报错 |
| `strict: true`，但 `strictPropertyInitialization: false` | DTO 用 `!: T` 声明，由 class-transformer 填充 | — |
| 禁止 `any`（`unknown` + 收窄） | 类型安全 | eslint |

### 13.2 命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 文件（类） | kebab-case + 类型后缀 | `user.controller.ts`、`base.dto.ts`、`redis.domain.ts` |
| 文件（测试） | 与被测文件同名 + `.spec` | `base.dto.spec.ts` |
| 类 | PascalCase + 类型后缀 | `UserService`、`CreateUserDto`、`AllExceptionsFilter` |
| 方法 | camelCase，动词开头 | `findAll`、`buildOrderBy`、`toOptionalNumber` |
| 常量 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE`、`BUSINESS_CODE` |
| 配置键（YAML） | kebab-case | `api-prefix`、`max-files` |
| 配置属性（TS） | camelCase | `apiPrefix`、`maxFiles` |
| Prisma 字段 | camelCase + `@map` snake_case | `userName` / `@map("user_name")` |
| 布尔量 | `is`/`has`/`enable` 前缀 | `isProduction`、`headersSent`、`enabled` |

### 13.3 注释规范（本仓库最鲜明的风格特征）

**注释写「为什么」和「边界」，不写「是什么」。** 代码本身已经说明了 what，注释的价值在于解释 why 和 why-not。

仓库里的范本（`libs/database/src/database.module.ts`）：

```ts
/**
 * 数据库模块。
 *
 * 为什么标 @Global：
 * 业务模块注入 PrismaService / DatabaseService 时不必逐个 import DatabaseModule，
 * 接入成本最低。代价是依赖关系不再显式。数据访问属于典型的「全局基础设施」，
 * 这里接受该取舍；若团队更偏好显式依赖，去掉 @Global 并让业务模块自行 import 即可。
 */
```

结构：**一句话说是什么 → 「为什么这样设计」→ 「代价是什么 / 什么情况下应该改」**。

必须写注释的场景：
1. **非显然的取舍**（为什么 Global、为什么不用现成库）。
2. **反直觉的实现**（`toOptionalNumber` 为什么要返回 `NaN` 而不是 `undefined`）。
3. **踩过的坑**（`PrismaPg` 第二个参数才认 schema）。
4. **文件头的职责声明**（每个 lib 入口 / 核心类）。

禁止的注释：
- `// 获取用户列表` 写在 `findAll()` 上面（废话）。
- 被注释掉的代码（用 git 管历史）。
- `// TODO` 不带负责人和条件（要么写 `// TODO(name): 待 XXX 完成后删除`，要么别写）。

### 13.4 格式与门禁

```bash
pnpm lint        # ESLint（antfu config）：2 空格、单引号、必须分号
pnpm format      # Prettier（⚠️ 脚本 glob 有 bug，见 17.4）
pnpm test        # Vitest 单测
pnpm test:e2e    # Vitest e2e
pnpm build       # tsc，同时验证 ESM 导入后缀
```

提交前必须全绿。`oxlint` / `stylelint` 未接入，不要假设它们会跑。

### 13.5 导入顺序

由 `@antfu/eslint-config` 自动排序，大致规则：

```ts
// 1. 类型导入（type-only）
import type { Foo } from '...';
// 2. 内置模块
import { readFileSync } from 'node:fs';
// 3. 第三方

// 4. 内部别名

// 5. 相对路径

```

每组之间空一行。不要手动调整顺序，`pnpm lint` 会重排。

## 14. 分层反模式清单

评审时逐条对照。**出现任意一条，打回重做。**

| # | 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- | --- |
| A1 | `libs/*` 里 import `apps/*` | 平台库被业务污染，无法独立复用/测试 | 把需要的抽象下沉到 libs，或反过来让 apps 依赖 libs |
| A2 | Service 注入 `@Req()` / `ExecutionContext` | Service 绑定 HTTP，无法纯单测，无法被其他模块复用 | 需要的信息由 Controller 解包成参数传入 |
| A3 | Controller 里直接 `prisma.xxx.findMany()` | 绕过业务规则与事务边界 | 走 Service |
| A4 | Service 返回 Prisma 模型给 Controller | `password`、`delFlag` 会泄露 | 返回 Response DTO |
| A5 | 手拼 `{ code: 0, data, message }` | 绕过拦截器，格式必然漂移 | `return data` |
| A6 | `throw new Error('xxx')` 表示业务失败 | 变成 500，客户端无法按码处理 | `BusinessException` |
| A7 | 在 Controller 里 `try/catch` 后返回错误体 | 丢堆栈、重复实现过滤器 | 让它抛，交给 `AllExceptionsFilter` |
| A8 | 跨模块直接查别人的表 | 表归属混乱，改表要改多处 | 调归属模块的 Service |
| A9 | 模块间双向依赖 / `forwardRef` | 循环依赖，初始化顺序不可控 | 抽出共享的第三个模块，或事件解耦 |
| A10 | 把会话/限流塞进 `CacheService` | 读失败降级为「未命中」= 免认证 | 用强一致 Redis 命令服务 |
| A11 | 在事务里删缓存/发消息 | 事务回滚但副作用已发生 | 提交后执行 |
| A12 | 业务模块读 `process.env` | 绕过配置校验，环境行为不可预测 | 配置域 |
| A13 | 往 `BUSINESS_CODE` 加业务错误码 | 通用码表被业务污染 | 模块内 `*.error.ts`，从段位分配 |
| A14 | 手写 `@ApiProperty()` | 与 `nest-cli.json` 的插件冲突，注释与装饰器双份维护 | 写 JSDoc |
| A15 | Response DTO 字段漏 `@Expose()` | 字段静默消失，排查成本极高 | 每个输出字段都标 |
| A16 | 列表接口不分页 | 数据量一大就 OOM | `paginate()` |
| A17 | 手改 `libs/database/src/generated/**` | 下次 `db:generate` 被覆盖 | 改 `.prisma` 后重新生成 |
| A18 | 为每个 Service 配一个纯转发的 Repository | 增加 30% 代码，零收益 | 满足 6.4 的触发条件才建 |

**Step 5 — 写 Service**

```ts
import { toDto, toPageDto } from '@app/common';
import { paginate, PrismaService } from '@app/database';
import { BusinessException } from '@app/core';
import { Injectable } from '@nestjs/common';

import { ROLE_NOT_FOUND } from './role.error.js';
import { CreateRoleDto, QueryRoleDto } from './dto/role.dto.js';
import { ResponseRoleDto } from './dto/response.dto.js';

@Injectable()
export class RoleService {
  constructor(private readonly prisma: PrismaService) {}

  async findAll(query: QueryRoleDto) {
    const data = await paginate(this.prisma.role, { ...query, where: { delFlag: '0' } });
    return toPageDto(ResponseRoleDto, data);
  }

  async findOne(roleId: number): Promise<ResponseRoleDto> {
    const role = await this.prisma.role.findFirst({ where: { roleId, delFlag: '0' } });
    if (!role) throw new BusinessException(ROLE_NOT_FOUND);
    return toDto(ResponseRoleDto, role)!;
  }
}
```

**Step 6 — 写 Controller**

```ts
import type { PageResponseDto } from '@app/common';
import { Controller, Get, Param, Query } from '@nestjs/common';

import { QueryRoleDto } from './dto/role.dto.js';
import { ResponseRoleDto } from './dto/response.dto.js';
import { RoleService } from './role.service.js';

/**
 * 角色模块
 */
@Controller('role')
export class RoleController {
  constructor(private readonly roleService: RoleService) {}

  /**
   * 分页查询角色
   * @remarks 默认按创建时间倒序，仅返回未删除角色。
   */
  @Get()
  findAll(@Query() query: QueryRoleDto): Promise<PageResponseDto<ResponseRoleDto>> {
    return this.roleService.findAll(query);
  }

  /**
   * 查询角色详情
   */
  @Get(':id')
  findOne(@Param('id') id: string): Promise<ResponseRoleDto> {
    return this.roleService.findOne(+id);
  }
}
```

## 16. 架构决策记录（ADR）

格式：**背景 → 决策 → 后果 → 什么情况下重新考虑**。新增决策时追加到本节，不要改写历史 ADR。

### ADR-001：HTTP 层用 Fastify 而非 Express

- **背景**：NestJS 默认 Express，但项目需要更低的序列化开销和更细的 hook 控制。
- **决策**：用 `@nestjs/platform-fastify`，Fastify 构造选项集中在 `libs/common/src/adapters/fastify.adapter.ts`。
- **后果**：`preParsing` hook 能在 JSON 解析**之前**拿到原始流，这是报文解密能实现的前提（Express 的 body-parser 中间件做不到这个时机）。代价：生态中部分 Express 中间件不可用，`@types/express` 相关写法要改。
- **重新考虑**：不需要。报文加密已深度依赖 Fastify hook。

### ADR-002：自建配置系统而非直接用 `@nestjs/config`

- **背景**：`@nestjs/config` 的 `validationSchema` 只做结构校验，不支持「多环境分层 + 强类型 + 启动时全量报错」。
- **决策**：三层 YAML 合并 + 域模型（`defineConfigDomain`）+ 一次性编译（`compileConfig`）。
- **后果**：配置错误在启动时**全部**暴露，格式统一为 `字段路径: 原因`；配置项有完整 TS 类型。代价：新增配置需要改两个地方（domain + YAML），比直接读 env 啰嗦。
- **重新考虑**：配置域超过 15 个时，考虑引入 schema 驱动的方案（zod）。

### ADR-003：Prisma 7 用驱动适配器而非内置引擎

- **背景**：Prisma 7 移除了 Rust 查询引擎，改为「查询编译器」。
- **决策**：`engineType = "client"` + `@prisma/adapter-pg`，连接池参数由 `database` 配置域控制。
- **后果**：连接池可精细调优（`max` / `idleTimeout` / `connectTimeout`），产物可被 bundler 正常打包。代价：`schema` 必须走 `PrismaPg` 第二参数，URL 上的 `?schema=` 只对 CLI 生效。
- **重新考虑**：不需要。

### ADR-004：统一响应信封 + 业务码

- **背景**：需要前端统一拦截、后端统一观测。
- **决策**：`{ code, data, message }`，成功 `code=0`，错误码复用 HTTP 语义 + 业务段位。
- **后果**：前端只写一处拦截器；错误可观测可统计。代价：HTTP 状态码与 `code` 存在冗余（`404` 出现两次），但换来「HTTP 层与业务层解耦」。
- **重新考虑**：不需要。**不要改成 `{ code, msg, data }`**（RuoYi 风格），会破坏所有前端。

### ADR-005：`@Global()` 只给基础设施

- **背景**：逐个 import 基础设施模块很啰嗦。
- **决策**：`AppConfigModule` / `CryptoModule` / `DatabaseModule` 全局；`CacheModule` / `SwaggerModule` 非全局。
- **后果**：常用能力零成本接入；缓存这种「可选能力」保持显式。代价：`SystemModule` 当前误标为全局（待整改）。
- **重新考虑**：当模块数超过 20 个、依赖关系难以追踪时，考虑全部去全局化。

### ADR-006：Keyv + 自写 RedisStore 而非 `cache-manager-redis-store`

- **背景**：`cache-manager` v7 的 Redis store 生态不统一，第三方包对 TTL 单位（秒/毫秒）处理不一致。
- **决策**：自己实现 `KeyvStoreAdapter`（`libs/cache/src/redis.store.ts`），TTL 统一毫秒，用 `PX` 命令。
- **后果**：TTL 语义完全可控（1..2147483647 毫秒，禁止 0）；连接生命周期集中管理；`clear()` 直接抛错防止误清库。代价：需要自己维护 ~80 行适配器代码。
- **重新考虑**：不需要。

### ADR-007：报文加密兼容 RuoYi 的 AES-ECB + RSA PKCS#1 v1.5

- **背景**：需要与既有 RuoYi-Vue-Plus 前端/Hutool 客户端互通。
- **决策**：不发明新协议，严格复刻 Hutool 的格式（AES-ECB/PKCS + RSA PKCS#1 v1.5）。
- **后果**：可直接对接现有客户端。代价：AES-ECB 本身不是理想模式（相同明文块产生相同密文），安全性依赖外层 HTTPS。
- **重新考虑**：新客户端可考虑 AES-GCM + RSA-OAEP，但需要双协议共存期。

### ADR-008：日志用 pino 多目标而非单一输出

- **背景**：需要同时满足「开发可读」「生产可采集」「错误单独告警」。
- **决策**：`pino` 多 target —— 控制台（pretty/JSON 可切）+ `gateway.log`（全量）+ `error.log`（仅 error），`pino-roll` 按大小 + 时间双维度轮转。
- **后果**：一个进程内三个输出，配置集中在一处。代价：`LoggerTransport` 必须管理 worker 生命周期，关闭时先 `ref()` 再 `end()`，否则丢尾部日志。
- **重新考虑**：接入日志平台后可去掉文件输出，只留 stdout（12-factor）。

### ADR-009：**当前无全局 ValidationPipe**（待决策）

- **背景**：DTO 上写满了 class-validator 装饰器，但没有任何 Pipe 执行它们。
- **现状**：所有 `@Body()` / `@Query()` 拿到的是原始 plain object，校验、类型转换、默认值、`@Transform` **全部不生效**。
- **影响**：这是当前最严重的功能缺口，任何依赖 DTO 校验的接口都是裸奔。
- **待决策**：补齐方式（全局 `ValidationPipe` + 自定义 `exceptionFactory` 拍平成 `FieldError[]`）。落地时需同步：
  - `transform: true`、`whitelist: true`、`forbidNonWhitelisted: true`
  - `exceptionFactory` 返回 `BusinessException.validation(errors)`
  - 补 `libs/core/src/pipes/` 下的 flatten 工具
  - 回归所有现有接口（开启 `forbidNonWhitelisted` 后，多传字段会 422）
- **状态**：🔴 未解决，优先级最高。

## 19. 术语表

| 术语 | 含义 |
| --- | --- |

| **Expand/Contract** | 三步迁移法：先扩展兼容、再迁移数据、最后清理旧结构 |
| **架构不变式** | 1.4 节的 7 条不可协商规则 |
| **ADR** | 架构决策记录，解释「为什么这样做」以及「什么情况下重议」 |
